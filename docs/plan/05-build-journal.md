# Build journal

What was built per step and why, for the owner to read; quiz questions per phase at the end of each phase section.

## Phase 0 — Bootstrap

### 0.1 — git init, ignore, node version
The repository was initialised on `main` with a pinned Node major (`.nvmrc` = 22) and an `.editorconfig` so every editor produces the same whitespace. The existing `.gitignore`, `CLAUDE.md` and `docs/plan/` were picked up as they were. Why `.env.*` is ignored but `.env.example` is force-included: real env files hold secrets and must never be committed, so a wildcard blocks every variant; the `!.env.example` exception lets the one file that documents variable names (without values) stay tracked so a fresh clone knows what to set.

### 0.2 — pnpm workspace + root package.json
The root `package.json` is private and only holds scripts, the pinned `packageManager` (pnpm 12.16.1) and TypeScript; `pnpm-workspace.yaml` says every folder under `apps/` and `packages/` is a workspace. `tsconfig.base.json` holds the strict compiler settings that each workspace extends, and the root `tsconfig.json` is a "solution" file that `tsc -b` follows through project references (it stays empty until step 0.3 adds the first workspace, so `pnpm typecheck` only becomes meaningful then). pnpm's `node_modules` is strict: a package can only import what it declares in its own `package.json`, so there are no phantom dependencies that work by accident on your machine and break in CI. The `workspace:*` protocol makes one workspace depend on another by linking the local folder instead of fetching from the registry.

### 0.3 — packages/shared skeleton
`@store/shared` holds what the API and web must agree on: money helpers, the API error-code enum with its HTTP statuses, and an empty `schemas/` folder for Zod. It ships TypeScript sources through `exports` (no build step), so the consumers' own tooling compiles it. The first test file pins down rounding, the negative/float guards and currency formatting. Integer cents because floats cannot represent 0.1 exactly, so sums drift and no longer match Stripe to the cent; `Intl.NumberFormat` over hand-formatting because it knows each currency's decimals, symbol position and locale grouping, which string concatenation gets wrong.

### 0.4 — apps/api skeleton
The API is an Express 5 app with one route, `GET /api/v1/health`, request logging through pino-http and a Zod-validated `env.ts` (the only place dotenv is imported). `createApp()` builds and returns the app and `index.ts` only reads config and calls `listen`; a Supertest test drives the app without a port. Why split: tests can create fresh isolated apps in milliseconds, and importing the app never has side effects such as binding a port. ESM in Node 22: the package is `"type": "module"`, so imports are real ES modules and relative imports must carry their file extension at runtime, which is why the source writes `./app.ts` and the build step rewrites it to `./app.js`.

### 0.5 — apps/web skeleton
The web app is a hand-assembled Vite + React 18 + TypeScript project using the SWC plugin, with Tailwind 3 (config + PostCSS), React Router and TanStack Query installed, and one page that shows `api: ok` from the health endpoint via a typed function in `src/api/health.ts` (no fetching inside components, per the guard-rails). One component test proves jsdom, Testing Library and jest-dom work together. The Vite dev proxy forwards `/api` to :3000, so the browser only talks to its own origin: cookies are same-origin and there is no CORS to configure locally. SWC (Rust) compiles TSX and applies React Fast Refresh much faster than Babel for the same result. React StrictMode intentionally mounts, unmounts and remounts components in development to flush out effects that are not cleanup-safe, so double logs in dev are expected and absent in production.

### 0.6 — lint + format
One root flat `eslint.config.js` lints every workspace with typescript-eslint's type-checked recommended rules, `react-hooks` for the web app, `import/order`, a ban on default exports (except tool configs and route pages) and a ban on `any` and `@ts-ignore`. Prettier is set to 100 columns, single quotes, trailing commas; `simple-git-hooks` installs a pre-commit hook (via `pnpm prepare`) that runs `lint-staged`. A deliberately bad file was staged to prove the hook blocks the commit with nine errors, then removed. Flat config is a plain JS array of config objects (explicit, composable, one file) replacing the legacy cascading `.eslintrc` with its implicit `extends` and per-folder files. Hooks only touch staged files because linting the whole repo on every commit is slow enough that people start bypassing the hook; CI still checks everything.

### 0.7 — docker compose for local services
`docker-compose.yml` runs Postgres 16 (database `ecommerce`, data in a named volume, healthcheck via `pg_isready`) and Mailpit (SMTP on 1025, web UI on 8025), both bound to 127.0.0.1 only. A one-line init script creates a second database, `ecommerce_test`, the first time the volume is created. `.env.example` documents every variable so far (`NODE_ENV`, `PORT`, `DATABASE_URL`, `DATABASE_URL_TEST`, `WEB_ORIGIN`, `LOG_LEVEL`). Why a separate test DB: integration tests truncate or roll back freely, which must never be able to wipe the data you are developing against. A healthcheck says whether a service is actually ready to accept work, while `depends_on` alone only orders container start; combining them (`condition: service_healthy`) is what makes "start the API after Postgres is ready" reliable.

### 0.8 — CI skeleton
`.github/workflows/ci.yml` runs on every push and pull request with two parallel jobs: `check` (typecheck, lint, format check) and `test` (Postgres service container, then `pnpm test`; a comment marks where `db:migrate` joins in phase 1). It could not be run here (no `act`, no remote), so it was validated by Prettier parsing it and by repeating the same commands in a clean clone. A service container is a Docker container GitHub starts beside the job and health-checks before your steps run, so tests talk to a real Postgres on `localhost:5432` just like locally. Caching the pnpm store (keyed on the lockfile) makes installs mostly local copies instead of downloads. `concurrency` with `cancel-in-progress` cancels the older run of the same branch when a new push arrives, saving free-tier minutes.

### 0.9 — README stub
The README is a deliberately small stub: a working title, one line on what the project is, a work-in-progress note and the commands to run it locally and to run the checks. GitHub repo creation and the first push were intentionally skipped; they wait for the owner's go and his choice of repository name. The stub is honest about what does not exist yet (migrations and seed arrive in phase 1) so a fresh clone is never misleading.

## Phase 1 — Database

### 1.1 — Drizzle setup
The API now has a Drizzle client (`postgres` pool with `max` 10 and an idle timeout), a Zod-validated `DATABASE_URL`, a `drizzle.config.ts` and a migrator script behind `pnpm db:migrate`. Migration 0000 is hand-written SQL: the `citext` extension and the `set_updated_at()` trigger function that every table will attach. Migrations are the source of truth because they are the exact, reviewed, replayable history that production runs; `drizzle-kit generate` writes that history as SQL files, while `push` diffs the schema against a live database and mutates it with no record, so it is for throwaway experiments only. The env is validated at boot so a missing or malformed variable stops the process with a clear message, instead of surfacing as a confusing failure on the first query.

### 1.2 — users, sessions, addresses
Three tables per the data model, with the shared id/timestamp columns in one helper file and `updated_at` bumped by a trigger attached in the migration. I read the generated SQL (it matched the schema, and I appended the two trigger lines by hand). A smoke test inserts a user, proves case-insensitive email uniqueness, cascades a delete to sessions and addresses, and proves the partial unique index. `citext` is text compared case-insensitively, so one email cannot register twice as `A@x.com` and `a@x.com` without remembering to lowercase everywhere. A partial unique index only covers rows matching its `WHERE`, which is how "at most one default address per user" is enforced while non-default rows stay unlimited. `ON DELETE CASCADE` means deleting a user silently deletes their sessions and addresses in the same statement: great for cleanup, dangerous if a table that must outlive the user (orders, later) were wired to cascade, which is why orders use a nullable, non-cascading `user_id`.

### 1.3 — catalog tables
Categories (self-referencing parent), products, variants, images and inventory are in migration 0002, with GIN indexes on `search_vector` and `attributes` and a trigger per table. `search_vector` is a stored generated column: Postgres recomputes `to_tsvector('english', name || ' ' || description)` on every write, so it can never go stale and the app never writes it; the test searches it with `to_tsquery` and shows stemming ("napping" matches "naps"). A B-tree orders and compares whole values (equality, ranges, sorting), while a GIN index maps each lexeme or JSON key to the rows containing it, which is what "contains this word/key" queries need. `options jsonb` is unique per product because one combination such as red + small must be exactly one sellable thing; without it the cart could hold two "identical" variants with different stock.

### 1.4 — cart and shipping tables
`carts`, `cart_items` and `shipping_methods` are in migration 0003. The one-active-cart-per-user rule is a partial unique index on `user_id WHERE status = 'active'`, so the database refuses a second live cart even if two requests race, while merged/converted/abandoned history and any number of guest carts (NULL user ids never collide) stay allowed. Cart items carry no price, only a variant and a quantity (checked 1 to 99, unique per cart), because the cart is re-priced from the catalog on every read. The test inserts a second active cart and expects a rejection, then shows a new one is allowed once the old one is converted.

### 1.5 — order, payment, webhook and history tables
Migration 0004 adds `orders`, `order_items`, `payments`, `webhook_events` and `order_status_history`, the `order_number_seq` sequence (the order number is a column default built from it) and the check constraints. The test proves a wrong total, a wrong line total and a duplicate webhook event id are all rejected, and that order numbers are unique and well-formed. Order items copy the product name, variant name, SKU, image and unit price instead of pointing at the live variant, because the catalog changes (renames, price changes, deletions) while an order is a legal record of what was agreed at that moment. A check constraint is the last line of defence: application code can have bugs or be bypassed by a script, but the database refuses an inconsistent row no matter who writes it.

### 1.6 — seed data
`src/db/seed/` holds the categories (5 pets, 20 sub-categories with per-pet accent colour and icon), 40 hand-written products, the two shipping methods and three demo users with argon2id hashes; `expand.ts` turns each product's option axes into variants with SKUs, prices, weights, image rows and deterministic stock (211 variants, 63 images, a few sold out and a few low). Every table is written with `INSERT ... ON CONFLICT DO UPDATE` keyed on slug, SKU, code or email (inventory is insert-only so a re-seed never resets stock), and a test proves two runs give identical counts. `pnpm db:reset` drops both schemas, migrates and seeds, and refuses to run in production or against a non-local host. `ON CONFLICT DO UPDATE` makes an insert into "insert, or update the row that already has this unique key", which is why the seed is idempotent; seeds are code rather than SQL dumps because code can derive 211 variants from 40 products, is type-checked against the schema, and cannot silently rot when a column changes. Images are AI-generated by a separate step rather than downloaded, so the rows and paths exist now and the files arrive later through `pnpm images:process` (sharp cover-crops to 1200 and 600 pixel WebP); the licence question becomes "which tool and prompt made this", recorded in `CREDITS.md`.

### 1.7 — test database harness
A vitest `globalSetup` migrates the test database once per run, and a `setupFiles` hook truncates every public table (list read from `pg_tables`) before each test and closes the pool after each file; both refuse to run unless the database name ends in `_test`. `fileParallelism: false` keeps files from sharing the database at the same time, and three factories (`createUser`, `createProduct({variants})`, `createCart`) build valid rows with unique slugs, SKUs and emails. A new test proves a row written in one test is gone in the next, and the earlier table tests were simplified to use the harness instead of cleaning up after themselves. Truncating per test is simple and, with these tiny tables, fast enough; the alternative (wrapping each test in a rolled-back transaction) is faster but breaks code that opens its own transactions, which checkout will.

## Phase 2 — API foundation

### 2.1 — request id and logging
Every request now gets an id: the caller's `X-Request-Id` if it looks like a safe id, otherwise a fresh UUID. It is set on `req.id`, echoed in the response header and used by `pino-http` as the log line's request id. The logger redacts the cookie, authorization and set-cookie headers, prints pretty output only in development and JSON otherwise. Tests capture the log stream to prove the id is on the access log and that secrets never appear. Learn: structured logs are one JSON object per line, so a log tool can filter on fields instead of parsing sentences; redaction exists because logs outlive and spread wider than the database; one id passed web, api and Stripe lets you follow a single checkout through all three systems' logs.

### 2.2 — domain errors and error middleware
`AppError(code, message, details)` is the only error services throw; its status comes from the shared code-to-status table, and small factories (`notFound`, `validation`, `conflict(code)` ...) keep call sites short. The error middleware is the one place errors become HTTP: `AppError` gives its own status, a `ZodError` becomes 400 with flattened issues, parser errors (bad JSON, too large) become 400/413, and everything else is logged with its stack and answered with a generic 500 in production. An unknown route falls through to a JSON 404. The shared package had to learn to be imported by the API (workspace dependency, `.ts` extensions in its relative imports, `allowImportingTsExtensions` in the base tsconfig) because the API compiles it under NodeNext. Learn: throwing a typed error keeps rules out of the HTTP layer, and never leaking a stack trace matters because a stack names files, libraries and queries an attacker can use.

### 2.3 — Zod validation middleware
`validate({ body, query, params })` parses each part with its Zod schema and stores the results on `req.valid`; a failure throws a `ZodError`, which step 2.2's middleware turns into a 400. Handlers read the values with `valid(req, schemas)`, which gives them their inferred types (coerced numbers, defaults applied). `respond(res, schema, data, meta?)` sends the `{ data, meta }` envelope and, outside production, first checks the data against the endpoint's schema, failing with a 500 if our own output drifts from the contract. Express 5 made `req.query` read-only, which is why parsed values go on `req.valid`. Learn: validating at the edge means everything inside the app can trust its types; validating output catches the bug in our tests instead of in the web client.

### 2.4 — security middleware
The app now runs `helmet`, CORS limited to `WEB_ORIGIN` with credentials, a global rate limit (429 in the normal error envelope, health exempt), signed `cookie-parser`, a 100 kB JSON limit and a CSRF origin check on every non-GET request except the Stripe webhook prefix. `trust proxy` is 1 only in production. A stricter limiter factory for login is ready for phase 6 and keys on IP plus email. Config is validated in `env.ts` (a production boot without `COOKIE_SECRET` fails) and passed into `createApp` as one `config` object. Learn: helmet sets headers such as `Strict-Transport-Security` (stay on HTTPS), `X-Content-Type-Options: nosniff` (no MIME guessing), `X-Frame-Options` (no clickjacking frames), a restrictive `Content-Security-Policy` and `Referrer-Policy`. Origin checking is enough with `SameSite=Lax` because the cookie is not sent on cross-site POSTs and a page cannot forge its `Origin`, so two independent layers must both fail. Rate limits are keyed by IP so one noisy client cannot starve others, and by email on login so one attacker cannot lock out a victim from everywhere.

### 2.5 — database health check and graceful shutdown
`GET /api/v1/health` now runs `select 1` raced against a 1 s timer and returns `{ status, db, version }` with 200, or 503 (`degraded`/`down`) plus a logged error carrying the request id. The version is read from `package.json` at startup. `index.ts` now keeps the server handle and, on SIGTERM/SIGINT, stops accepting connections, closes idle sockets, closes the DB pool and exits 0; if anything has not finished after 10 s it exits 1. The logic lives in `lib/shutdown.ts` with the exit function injected so tests can check it, and I also sent a real SIGTERM to the running server and saw "shutdown complete". Learn: platforms stop a service by sending SIGTERM and killing it after a grace period, so finishing in-flight requests and releasing connections prevents dropped checkouts and leaked database connections on every deploy.

### 2.6 — module layout and router mounting
`src/modules/index.ts` mounts the `catalog`, `auth`, `cart`, `checkout` and `admin` routers at the root of `/api/v1`; each folder has a `router.ts` exporting an empty router so later phases only add files. Routers declare their full sub-paths (`/products`, `/auth/login`), so a path from the API contract can be found by searching the code. `.env.example` was already updated in 2.4. A final test checks the phase's acceptance criterion: a bad JSON body, an unknown route, a foreign-origin POST and a database outage each give the right status and a log line carrying the request id. Router variables carry an explicit `Router` type annotation because TypeScript otherwise refuses to name the pnpm-internal type.

## Phase 3 — Catalog API

### 3.1 — shared catalog schemas
`packages/shared/src/schemas/` now has `common.ts` (the `{ data }` / `{ data, meta }` envelopes, pagination meta and query) and `catalog.ts` (category, product card, variant, product detail, facets and the list query). The list query schema moves every `attr.<key>` parameter into an `attr` record, splits comma lists into arrays, coerces numbers, turns `inStock=true|false` into a boolean, caps `limit` at 100, rejects `minPrice > maxPrice` and strips unknown parameters. `respond()` from step 2.3 now takes the whole envelope schema so the web can parse responses with the same schema the API validated against. Learn: sharing one schema file means a change to a response shape is a type error in both the API and the web at once, instead of a bug found in the browser.

### 3.2 — category endpoints
`GET /api/v1/categories` returns the whole tree and `GET /api/v1/categories/:slug` one category with its children, both validated against the shared schemas. The repo does one query with a grouped count of active products joined in (not one count per category), the service builds the tree and rolls children's counts up into their parent, and the router only validates and responds. A missing slug is a `notFound()` thrown by the service, because the repo never throws domain errors. The factories gained `createCategory` and options on `createProduct` (category, attributes, images, stock details) that the later steps use. Learn: one grouped join keeps the endpoint at constant query count however many categories exist.

### 3.3 — product list: base query, pagination, sort
`GET /api/v1/products` returns active products as cards: a join to a per-product summary of active variants (min and max price, currency, any stock left), the category slug, and one primary image fetched for the page's products in a second query (`DISTINCT ON`, product-level images first). A separate count query gives `meta.total`. Sorting has a map for `price_asc`, `price_desc`, `newest` and `name`, every one ending in `products.id` so ties cannot reorder between pages; `relevance` without a search term falls back to newest. Learn: offset pagination (`LIMIT/OFFSET`) is simple and lets the shopper jump to page N; keyset pagination is faster for deep pages and infinite feeds but cannot jump and needs a stable sort key, and with 40 products (and at most a few thousand ever) the offset cost is invisible, so simple wins. `EXPLAIN ANALYZE` on the dev seed (40 products, 211 variants): sequential scans on the three small tables, a hash aggregate for the variant summary, a hash join, an index scan on `categories_pkey`, top-N sort, 0.56 ms; at this size Postgres rightly ignores indexes, and the GIN and foreign key indexes matter once the tables grow.

### 3.4 — product filters
The list accepts `category` (the category plus its children), `minPrice`/`maxPrice` (a product matches if any active variant is in range), `inStock`, and `attr.<key>=v1,v2`. Each filter is a Drizzle `sql` fragment returned by one `filterConditions()` function and combined with `and()`, and the list and count queries both use it so `meta.total` always matches. Attribute filters use jsonb containment (`attributes @> {"material":"plush"}`), OR-ed within a key and AND-ed across keys, with values bound as parameters. Tests cover each filter, an injection attempt and a combination with sort and paging. Learn: `@>` can use the GIN index on `attributes`, while `attributes->>'material' = 'plush'` cannot, and binding values as parameters is what stops SQL injection.

### 3.5 — full-text search
`q` is compiled with `websearch_to_tsquery('english', q)` and matched against the generated `search_vector` with `@@`; `sort=relevance` (the default when `q` is present) orders by `ts_rank`, then newest, then id. One or two characters, and queries made only of stop words, fall back to a case-insensitive substring match on the name, with `%` and `_` escaped. Tests show "rope" finding both rope toys, "parrot" finding a bird product through its description, stemming, quoted phrases and exclusion, and that a real typo finds nothing: typo tolerance is not promised, and the contract now says so. Learn: a `tsvector` is the text reduced to stemmed, de-stop-worded lexemes with positions; a `tsquery` is the same for the search, and `@@` asks whether the vector satisfies the query; `plainto_tsquery` ANDs all words and has no syntax, `websearch_to_tsquery` adds quotes, `or` and `-` and never raises a syntax error on user input, so it is the safe choice for a search box; `ts_rank` scores by how often and how densely the words appear.

### 3.6 — facets
The list response now carries `facets: { attributes, price }` next to `data` and `meta`. Attribute counts come from one grouped query that expands each product's jsonb with `jsonb_each_text`, restricted to the `FACET_KEYS` (`pet`, `material`, `brand`, `ageStage`); the price range is the min and max over the same products. The facets are computed over the browsing scope (category with children, plus the search term) and deliberately ignore the attribute, price and stock filters, so the other values keep their counts and the shopper can switch between them. Every key is always present, empty if nothing matches. The filter code was split into `scopeConditions` (shared by list, count and facets) and `filterConditions` (scope plus narrowing filters). Learn: grouping by key and value in a single pass is what makes the filter UI data-driven without a query per filter.

### 3.7 — product detail
`GET /api/v1/products/:slug` returns the product with its active variants (cheapest first, with `compareAtPriceCents`, `isDefault`, `available` and `lowStock`), images in sort order (variant-specific ones carry their `variantId`), the public attributes, `optionKeys` split out of the attributes jsonb, a root-first breadcrumb (parent category then category) and the price range and `inStock`. Availability is `quantity - reserved > 0` and low stock is available units at or below the variant's threshold; the raw numbers never leave the service, and a test checks the JSON for any stock field names. Draft, archived, unknown and no-active-variant products are all the same 404. Learn: exposing booleans instead of counts avoids leaking sales velocity, and keeping the rule in the service means the router and the repo stay free of business logic.

### 3.8 — caching headers
Catalog GETs (`/categories`, `/categories/:slug`, `/products`, `/products/:slug`) now send `Cache-Control: public, max-age=60, stale-while-revalidate=300`; Express's default weak `ETag` is already on every JSON response and a conditional request gets a 304. The header is applied by a middleware scoped to those paths (the catalog router is mounted at the API root, so an unscoped one would have leaked onto cart and account), and the error handler overwrites it with `no-store`, so a 404 or 400 is never cached as data. The contract documents that an admin change can lag up to 60 s publicly. Learn: `max-age` lets browsers and the CDN reuse a response without asking; `stale-while-revalidate` lets them serve a slightly old copy instantly while fetching a fresh one in the background; the ETag lets a client that does ask pay only for a 304 instead of the whole body.

## Phase 4 — Web foundation

### 4.1 — Tailwind and design tokens
Colours live as plain CSS variables in `src/styles/tokens.css`; `tailwind.config.ts` only gives them utility names (`bg-primary`, `text-pet-strong`), so putting `data-pet="cat"` on any wrapper re-themes every `pet-*` utility beneath it without JavaScript. Each pet defines three roles: a bright `accent` for fills (text on it is always ink), a pastel `soft` for backgrounds that sits well next to the pastel product photos, and a dark `strong` shade for text. A vitest file parses `tokens.css` itself and asserts WCAG AA (4.5:1) for every text pairing the UI uses, so a colour edit that breaks contrast fails the build. Fonts are Fredoka (rounded display) and Nunito Sans (body) from `@fontsource-variable`, bundled by Vite: no request to Google at runtime, one file per font covers every weight. The trade-off of utility CSS is long class lists in exchange for no naming, no dead CSS and a design system enforced by the config; the base layer (`globals.css`) holds the focus ring and the reduced-motion rule.

### 4.2 — UI primitives
`components/ui/` has Button, Input, Select, Checkbox, Badge, Skeleton, Dialog, Toast, Price, Spinner and VisuallyHidden, each with a test of its accessibility contract (role, accessible name, keyboard, described-by). Form controls require a `label` prop, so an unlabelled field cannot be written; the accessible name is what a screen reader speaks and what Testing Library's `getByRole(..., { name })` queries, which is why the tests double as an accessibility check. Dialog is a native `<dialog>` opened with `showModal()`, so the browser supplies the focus trap (everything behind is inert), Escape and focus return. Toast keeps two live regions (polite for info/success, `role="alert"` for errors) mounted before any message exists, because screen readers only announce changes inside a region that was already there; error toasts never auto-dismiss.

### 4.3 — layout
`components/layout/` holds Container (the single source of page width and gutters), SkipLink, Header, AccountMenu, SearchBox, MobileNav, Breadcrumbs, Footer and `AppLayout`, the frame that renders every route through `<Outlet />`. Landmarks are `header`, two labelled `nav`s, `main` and `footer`, and the skip link is the first tab stop; on phones the search wraps to its own full-width row so the top row (menu, logo, account, cart) fits at 360 px. The pet navigation reads a typed constant in `lib/pets.ts` (slug, name, `data-pet` accent, icon) so the shell needs no request; phase 5 can replace it with category data from the API if we want admin-editable categories. The cart badge count is a prop, not a fetch, because the cart feature (phase 7) will own that number. Landmarks matter because screen-reader users jump between them instead of reading linearly.

### 4.4 — routing
`routes.tsx` is one table of every route, wrapped in `AppLayout`; checkout, confirmation, account and admin use route-level `lazy()` and the build confirms each becomes its own small chunk, while the storefront pages stay in the main bundle. The data router (`createBrowserRouter`) is used instead of `<Routes>` because only it supports `lazy`, `errorElement` and later loaders. A pathless child route carries the `errorElement`, so when a page throws, the header and footer stay and only the main area shows "Something went wrong" (React would otherwise unmount the whole app to a blank page); the layout has its own bare fallback if it is the thing that breaks. `ScrollRestoration` lives in the layout. The router is created in `main.tsx`, not at import time, because creating a browser router reads `window`. Pages are minimal placeholders that say which phase builds them; `NotFoundPage` and `RouteErrorPage` are already real, so 4.7 only needs the Loading polish and Home.

## Phase 6 (API) — Auth and accounts

### 6.1 — password hashing + session store
`password.ts` wraps argon2id (64 MiB, 3 passes, 1 lane) and also owns a lazily computed dummy hash that login will verify against when an email is unknown, so both failures cost the same time. `sessions.ts` mints a 32-byte random token, stores only its SHA-256 in `sessions.id`, and `getSession` joins the user with explicit columns (the password hash can never leak upward), rejects expired rows in the query, and slides the expiry at most once an hour. `deleteOtherSessions` and `purgeExpired` cover password-change revocation and cron-less cleanup.
Learn: argon2id beats bcrypt because its memory cost makes GPU cracking expensive and bcrypt is capped at 72 bytes; a session fixation attack plants a known session id before login, so login must always issue a fresh one; sliding expiry keeps active users signed in without a write on every request.

### 6.2 — cookie + auth middleware
`lib/cookies.ts` is the only place the `sid` cookie's attributes are decided (HttpOnly, SameSite=Lax, Secure in production, path `/`, 30 days, no Domain), and the clear call reuses them because a browser ignores a clear whose attributes differ. `attachUser` loads the user from the cookie on the personal routes only and never rejects: no or bad cookie means `req.user = null`, while a down database still surfaces as a 500. `requireUser` answers 401, `requireAdmin` answers 401 for anonymous and 403 for customers.
Learn: HttpOnly hides the cookie from XSS, SameSite=Lax withholds it from cross-site POSTs, Secure keeps it off plain HTTP; the middleware is tested on a tiny standalone app before any real route depends on it.

### 6.3 — register / login / logout / me
Shared `RegisterSchema`, `LoginSchema`, `UserSchema` (strict, so a stray hash fails in dev/test) and `UserResponseSchema` are the single contract for API and web. Register inserts with `ON CONFLICT DO NOTHING` (409 when nothing came back); login verifies against the real hash or a dummy one so an unknown email costs the same as a wrong password, answers with one generic message, and always destroys the session cookie that arrived before issuing a new id. The credential limiter (10 per 15 min, keyed by IP + normalised email) sits before validation, and `onLogin` is an empty hook where phase 7.4 plugs in the cart merge.
Learn: NIST asks for length and a block-list instead of composition rules; registration may reveal that an email exists but login must not; the fixation fix is "never reuse a session id across a privilege change".

### 6.4 — account and address endpoints
`/account` (names), `/account/password`, address CRUD and the empty-for-now order list live in `modules/account`, all behind `requireUser` and all scoped by `req.user.id`, never by an id from the request. The password change verifies the current password, rehashes, and deletes every other session; a wrong current password is a field error (400) so the web does not mistake it for an expired session. Address writes run in a transaction that first locks the user row, demotes the previous default and then writes (the partial unique index would reject the other order), and a foreign id fails inside the transaction so even the demotion rolls back.
Learn: IDOR means trusting an id from the URL, fixed by putting the owner in the WHERE clause and answering 404 for both "missing" and "not yours"; `SELECT ... FOR UPDATE` turns a race into a queue; revoking other sessions is what makes a password change actually evict an attacker.

## Phase 7 (API) — Cart

### 7.1 — cart identity
`withCart` decides which cart a request works on: the signed-in user's single active cart, or the guest cart named by the signed `cart_id` cookie, creating either lazily on first use. The cookie only counts if its HMAC verifies and the row is still an active, ownerless, unexpired cart; for a user the cookie is ignored. The cart id therefore always comes from the server, never from a body or URL, which is the whole IDOR defence for the mutation steps. Races on a user's first cart are absorbed by `ON CONFLICT DO NOTHING` plus a re-read.
Learn: signed cookies stop tampering but are readable, encrypted cookies hide the value too (not needed for a uuid); the cart is a server resource keyed by identity, so the client never sends a cart id; lazy creation avoids one empty row per bot.

### 7.2 — cart read with repricing
`loadCart(tx, cartId)` joins each line with its variant, product, inventory and picture (variant image, else product image) in one query plus one for images, prices it at today's catalog price, and derives `available` (stock minus reserved) and `maxQty` (capped at 99). Archived products or variants are deleted from the cart with a `VARIANT_UNAVAILABLE` warning, over-stock lines are clamped and the clamp is saved (`QTY_REDUCED`), and a sold-out line stays visible but out of the totals (`OUT_OF_STOCK`). The cart is locked while it is read because the read can write. Not built: the contract's "price changed" warning, since the cart deliberately stores no price to compare.
Learn: re-pricing on read means stale prices cannot exist; repairing on read makes the cart converge instead of repeating the same warning; a read that writes needs the same lock as a write.

### 7.3 — cart mutations
`addItem`, `updateItem`, `removeItem` and `clear` each run in one transaction: lock the cart row, change it, slide its expiry, and return the whole re-priced cart from that same transaction. Adding is cumulative and the total (`inCart + quantity`) is checked against `min(99, available)`, refusing with 409 `OUT_OF_STOCK` and `{ maxQty, inCart, requested }`. The routes take no cart id at all (it comes from `withCart`), and every item lookup filters by both item id and the caller's cart id, so a foreign line is a 404. The parallel-add tests fire two (and ten) simultaneous requests at one cart and prove stock is never exceeded.
Learn: `SELECT ... FOR UPDATE` makes concurrent requests on one row take turns, so check-then-write becomes safe; returning the whole cart avoids a second GET that might show something the mutation did not produce; carts do not reserve stock, checkout does.

### 7.4 — merge on login
`mergeGuestCart(guestCartId, userId)` runs from `onLogin` after a successful login or registration. In one transaction it locks the guest cart, then the user's cart (created if missing), and walks the guest lines in a fixed order: same-variant quantities are summed and limited to `min(99, available)`, never below what the account already had; unbuyable lines are dropped; the guest cart is marked `merged` so a second login with the same cookie adds nothing. The rules are written above the function and again in the decisions log. A failure inside leaves both carts untouched (tested by making an insert throw), and a failed merge never fails the login.
Learn: a fixed lock order (guest, then user) prevents deadlocks; marking the source `merged` inside the same transaction makes the operation idempotent under double submits; "sum then clamp" is easy to say, the edge cases (stock below the user's own quantity) are the real design.

### 5.2 — ProductCard and ProductGrid

The image is a square box with `width`/`height`, `alt` from the API, `srcset` offering the 600 px twin next to the 1200 px original, and `loading="lazy"` except for the first row when the page asks for it. `ProductGrid` lays cards out 2/3/4 columns, fires `track('view_item_list')` once per distinct list, and `ProductGridSkeleton` is the loading state (home now uses both). ### 5.3 — PLP: list and URL state

### 5.4 — PLP: filters and sort
The filter panel is built from the API's `facets`: an in-stock checkbox, two price boxes, and one `fieldset` with a `legend` per attribute (Material, Age stage, and so on) whose checkboxes show counts. ### 5.5 — Search box
The header and drawer search boxes already navigated to `/search?q=`; now they read the query back from the URL, so on the search page the box shows what you searched and follows Back, another link, or leaving the page (it empties). The sync is done by adjusting state during render instead of in an effect, so there is no frame with the old text. The API's search matches word forms but does not correct typos, so the empty state says to check the spelling. Learn: the URL is the one source of truth for the query, and the input is only a view of it plus the draft being typed.

### 5.6 — PDP: layout and gallery
`/products/:slug` shows breadcrumbs from the API's category trail, a gallery, the name, the default variant's price (with compare-at struck through), description and an attributes list; an unknown slug shows the not-found page and a failed request shows a retry. `<Seo>` uses the product name and the first 155 characters of the description, with a canonical to the plain product URL, and `track('view_item')` fires once per product. ### 5.7 — PDP: variant picker

## Phase 8 (API) — Checkout and Stripe

### 8.1 — shipping quotes
`shipping.ts` is a pure function pair: `shippingPriceCents` (base plus per started kilogram, zero once the subtotal reaches the free threshold) and `quote` (prices every active method, cheapest first, stable on ties). `GET /checkout/shipping-methods?country=` re-prices the caller's own cart through `getCart`, so weight and subtotal come from the server and sold-out lines do not count. The country is validated against a short allow-list that now lives in `@store/shared`, because the address form in 8.2 needs the same list.
Learn: carriers bill per started kilogram, which is why it is `ceil`; keeping the pricing free of database imports is what makes the boundary cases (4899 vs 4900 cents) cheap to test.

### 8.2 — shared checkout schemas
Everything the checkout endpoints and the web steps need is now in `@store/shared`: the typed-in address (`CheckoutAddressSchema`), the request, the response with its server-computed totals, the full `OrderSchema` for confirmation pages, a status-polling response and an order-number params schema. The request has no price, total or cart id on purpose: Zod strips unknown keys, so a client that sends `totalCents` is simply ignored. Orders are returned through a looser address schema than the one used for input, so shrinking the country list later never makes an old order unreadable.
Learn: validating at the edge means the service receives already-trimmed, upper-cased, typed data; schemas shared with the web are the contract, so a drift is a compile error instead of a runtime surprise.

### 8.3 — Stripe client wrapper
`lib/stripe.ts` hides the official SDK behind a five-method `PaymentGateway` (create, update amount, retrieve, cancel, construct webhook event) that speaks in our own types. The SDK is created once with its API version pinned, a 10 s timeout and two automatic network retries; every create carries an idempotency key, which is what makes those retries (and a crash between "Stripe answered" and "we stored the id") safe. The webhook check runs the SDK's real signature verification, and the three keys are validated at boot: only `sk_test_`, `whsec_` and `pk_test_` prefixes pass, and the first two are required in production. With no key the app still boots and payment calls fail with a clear 502.
Learn: a PaymentIntent is one attempt to collect one amount, a Charge is a single card try attached to it; pinning the API version stops a dashboard upgrade from changing payloads under us; an idempotency key turns "retry until it works" from dangerous into harmless.

### 8.4 — place order
`placeOrder` is two phases. In one transaction it locks the cart, then every involved inventory row in variant-id order, gives back the reservations of the cart's existing pending order (so a shopper holding the last unit can re-submit), re-prices the cart (any warning is a 409 `CART_CHANGED`), computes the total from database prices plus the shipping rule, reserves each line with a conditional `UPDATE`, and writes the order, its snapshot items and a `payments` row. Only after the commit does it create or update the Stripe PaymentIntent (idempotency key `order:<id>`), because no network call may happen while row locks are held; if that fails for an order that never had an intent, the order is cancelled and the stock released. The cart is converted only when payment is confirmed (8.5), and a signed `last_order` cookie gives a guest access to the order they just placed.
Learn: a reservation holds stock without removing it, so abandoned payments are reversible; locking rows in one global order is what makes two crossing carts safe; the "outbox" gap (committed order, no intent yet) is accepted and closed by the 8.7 sweeper.

### 8.5 — webhook endpoint
`POST /webhooks/stripe` is mounted before `express.json()` with `express.raw`, because the signature covers the exact bytes Stripe sent; a bad or missing signature is a 400 and nothing is stored. Each verified event is handled in one transaction that inserts the `webhook_events` row (the Stripe event id is the primary key), locks it, skips it if `processed_at` is already set, runs the handler and sets `processed_at`; if the handler throws, everything rolls back, the error is stored on the event row and the answer is 500 so Stripe redelivers. `payment_intent.succeeded` checks the amount and currency against the order, then marks it paid, turns the reservation into a stock decrement, converts the cart and writes history; failed, canceled and fully-refunded charges are handled as the plan says.
Learn: why 200 fast but only after the event is durably stored; why redelivery makes handlers idempotent-or-bust; why a mismatching amount leaves the order pending and logs an alarm instead of shipping.

### 8.6 — order status and the test simulator
`GET /checkout/orders/:number/status` returns `{ status, paymentStatus }` for the confirmation page's polling, and `GET /checkout/orders/:number` returns the whole order for guests too. Access is the signed-in owner or the browser holding the signed `last_order` cookie, and a missing order and someone else's order both answer the same 404, so numbers cannot be probed. `POST /test/webhooks/simulate` exists only when `NODE_ENV=test`: it builds the event Stripe would have sent for an order's intent and runs it through the same `processStripeEvent`, so CI and Playwright can pay an order without the Stripe CLI.
Learn: possession of a signed cookie is a capability, so keep it narrow (one order number, two hours); a test-only route is safest when it is simply not mounted elsewhere instead of being guarded by a flag at request time.

### 8.7 — stale reservation release and reconciliation
`releaseStaleReservations` looks at every order still `pending_payment` after 30 minutes and asks Stripe what really happened: a succeeded intent is confirmed through the same `confirmPayment` the webhook uses, a processing one is left alone, and anything else has its intent cancelled first (so a late tab cannot still pay) and then the order cancelled and the stock returned. Each order is handled separately, so one failure is counted and retried on the next sweep. It runs every five minutes inside the API process, guarded by a Postgres advisory lock so two instances never sweep at once, and is off with `ENABLE_JOBS=false` or without a Stripe key.
Learn: webhooks are best-effort, so something must reconcile with the provider's own records; cancel-then-check handles the race where the customer pays during the sweep; an advisory lock is a cheap "only one" without a scheduler service.

## Phase 6 (web) — Sign-in and account

### 6.5 — auth state and route guards
On boot the web asks `GET /auth/me` once, because the session lives in an httpOnly cookie the page cannot read. A 401 is the normal answer for a visitor, so `fetchMe` turns it into `null` and `useAuth()` reports `loading`, `authenticated` or `anonymous`. Login and logout write the `['me']` cache directly, which flips the header menu (name, My account, Sign out) and the guards with no extra request. `RequireAuth` and `RequireAdmin` are layout routes that send an anonymous visitor to `/login?next=<where they were going>`; `next` must be a same-site path, otherwise the login page would be an open redirect. The guards only decide what is shown: the API checks the session and the role again on every request.
Learn: a 401 on the "who am I" call is data, not a failure; a guard is a courtesy to the user, never the security boundary.

### 6.6 — login and register pages
Both forms use React Hook Form with the shared Zod schemas as the resolver, so the browser enforces the same rules as the API (the email is trimmed and lower-cased on the way out, a common password is refused). A rule only the server knows is copied from `details.fieldErrors` onto the field it names and that field takes focus; a taken email (409) lands on the email field, while a wrong password (a deliberately vague 401) is a form-level alert, because telling which half was wrong would help an attacker. After success the page goes to `?next=` if it is a same-site path, else home (register goes to the account page), and the password field has a show/hide button and the right `autocomplete` values so password managers work. Errors are tied to inputs with `aria-describedby` and `aria-invalid`.
Learn: validating twice (browser for speed, server for truth) is only safe when both use one schema; the first invalid field must get focus or a keyboard user does not know the submit failed.

### 6.7 — account area
`/account` is one lazy chunk behind `RequireAuth` with a side nav (wrapping pills on a phone, a column from `md`): Profile edits the two names (the email is shown but fixed), Security changes the password, Addresses lists, adds, edits and deletes with a native dialog and a confirmation, and Orders reads the endpoint that stays empty until phase 9. Every form is React Hook Form with the shared schema; a wrong current password comes back as a 400 field error, so it shows under that input and the user stays signed in instead of being sent to login. Address writes invalidate the whole list because setting a default demotes another row on the server and the cache must show exactly one default. The country is a native select built from ISO codes with names from `Intl.DisplayNames`, and long names and addresses wrap inside their cards instead of widening the page.
Learn: a server field error and a client rule should look identical to the user; after a write that changes other rows, refetching beats patching the cache by hand.

## Phase 7 (web) — Cart

### 7.5 — cart state and add to cart
`useCart()` reads `GET /cart` into the `['cart']` query and feeds the header badge. Quantity changes and removals are optimistic, as the plan says: before the request goes out the cache is rewritten with the expected cart (recomputed in integer cents), if the server refuses the cache is put back and refetched, and when it answers the whole real cart replaces the guess. All cart writes share one mutation scope so they run one after another; otherwise three quick taps on "+" make three requests whose answers can arrive in the wrong order. The PDP button now posts the variant, shows a spinner while it waits, tracks `add_to_cart`, and shows a toast with a "View cart" button; a 409 `OUT_OF_STOCK` becomes a sentence with the real numbers ("Only 3 available, and you have 2 in your cart."). The API reports a warning only once, so the web parks every warning it receives until the shopper dismisses it, and it reads warning codes as plain strings so a code from a newer API cannot break the cart.
Learn: `onMutate` snapshots and writes the guess, `onError` restores, and the server's answer is the final truth; optimistic UI is only safe when the rollback path exists and the writes are ordered.

### 7.6 — cart page and mini cart
`/cart` shows each line with its photo, name, variant, unit price, a quantity stepper, a remove button and the line total, then a summary with the subtotal, a "free shipping over €49" progress hint and "Proceed to checkout". The same lines and summary (compact) fill a drawer that opens from the header icon, so there is one implementation to fix. Warnings from the API show on the line they are about (quantity lowered, price changed) with an OK button, a removed or unknown one goes to a banner, and a sold-out line is greyed, struck through, kept out of the total, and blocks checkout with a stated reason. The typed quantity is applied on blur or Enter, the buttons at once, and the step stops at the line's `maxQty`. On a phone the summary sticks to the bottom edge, so the total and the checkout button stay in reach however long the cart is; the end-to-end tests cover the guest cart (add, reload, change, remove, empty), the stock message and the merge on sign-in.
Learn: the cart is where stale data hurts most, so it is re-read often (15 s) and every answer carries the whole cart; a disabled button needs a visible reason, or the shopper is stuck without knowing why.

## Phase 9 (API) — Orders, inventory rules, email

### 9.1 — order state machine
`modules/orders/state-machine.ts` is a table of allowed moves (`pending_payment -> paid|cancelled`, `paid -> processing|refunded|cancelled`, and so on) plus a pure `stockEffect(from, to)` that says whether stock is committed, released, restocked or left alone. `applyTransition` is the only code that writes an order's status: it checks the table, adjusts inventory, updates the payment row, spends the cart on `paid` and writes the history row, all inside the caller's transaction. The webhook, the sweeper, the checkout rollback and the admin service all call it, and the admin service does the Stripe refund or intent cancel first, before the transaction.
Learn: an explicit table makes every rule visible and testable in one place, where scattered `if`s let two code paths disagree; do the irreversible network step first and make it idempotent, so a failure afterwards is just a retry.

### 9.2 — customer order endpoints
`GET /account/orders` now carries an item count and up to four thumbnails per order, fetched with a single query for the whole page. `GET /account/orders/:number` returns the full order plus a timeline of `{ status, at }` built from the history table with the staff-only parts (actor, note, internal alarms) removed. The query includes the owner's id, so somebody else's order, a guest's order and a missing one are one and the same 404. `toOrderDto` is now the single mapper from a database order to the shared `Order` shape, used by checkout and account.
Learn: IDOR is fixed in the query, not in a check afterwards; answering 404 instead of 403 stops the endpoint from confirming which order numbers exist.

### 9.4 — email infrastructure
`lib/mailer.ts` builds a nodemailer transport from the environment: Resend's SMTP endpoint when `RESEND_API_KEY` is set, any `SMTP_URL`, Mailpit in development, or a disabled transport in production when nothing is configured (the API still boots). The two templates are plain functions from the shared `Order` to `{ subject, text, html }`, with inline CSS, the brand coral, escaped customer text and money from `formatMoney`. Emails are not sent directly: `email_outbox` (migration 0006) holds one row per owed email, and `drain` claims due rows with `FOR UPDATE SKIP LOCKED`, sends them and stamps `sent_at`, with exponential backoff on failure.
Learn: writing "an email is owed" in the same transaction as the change is what makes a crash harmless; `SKIP LOCKED` lets several instances share a queue without sending twice; plain SMTP keeps dev and prod on one code path.

### 9.5 — emails hooked into status changes
`applyTransition` queues the confirmation when an order becomes `paid` and the shipped email when it becomes `shipped`, inside the same transaction as the status change, with a unique key per kind and order so a replayed webhook queues nothing new. After the commit the webhook, the test simulator and the sweeper kick the drain in the background, and a 30-second timer picks up anything left over. A mail failure therefore never fails a webhook.
Learn: an outbox moves "send the email" from the request path to a retryable background step; the unique key makes enqueue idempotent, so the webhook's own idempotency carries over to email.

### 9.6 — inventory invariants test
`inventory-invariants.test.ts` runs seeded random sequences of checkouts, payments, intent cancellations, admin moves, dashboard refunds and stale sweeps, some raced in pairs, over variants with only a few units. After every step it asserts that stock is never negative, `reserved` never exceeds `quantity`, `reserved` equals the units in pending orders, and `quantity` equals the starting stock minus the units of orders that really took stock. The expectation is derived from order rows, not from the code's counters, and a failure message names the seed and step.
Learn: a property test states what must always be true and lets random sequences hunt for the counterexample; seeding the generator makes a failure replayable; checking against independently derived totals is what separates a test from a restatement of the code.

## Phase 10 (API) — Admin

### 10.1 — admin router, guard, audit and stats
`createAdminRouter` mounts `requireAdmin` and an audit middleware once on `/admin`, so every route added to it later is protected and logged by default: a guest gets 401, a customer 403, and the guard runs before validation so a stranger learns nothing about a route. Each mutation writes one structured log line with the request id, the user id, an action name, the target and the final status when the response finishes. `GET /admin/stats` returns today's order count, 30-day revenue (paid and still standing orders only) and the number of variants whose available stock is at or below their threshold.
Learn: guarding a prefix beats guarding routes because the safe state is the default; logging on `finish` captures failures and refusals as well as successes; "available" (quantity minus reserved) is the number that matters for restocking.

### 10.2 — products, variants, images and inventory
`/admin/products` lists every status with page, `q` (name, slug or SKU, with LIKE wildcards escaped) and a status filter, and creating a product writes the product, its variants, their inventory rows and its images in one transaction, with a slug generated from the name. Variants have their own endpoints and keep exactly one default; images are managed as a whole list of URLs inside the product (no uploads, because the stack has no object storage); stock is set with `PATCH /admin/inventory/:variantId` as an absolute number plus a reason, refused below what unpaid orders reserved, and every real change is recorded in the new `inventory_adjustments` table. Duplicate SKUs answer 409 both by a friendly pre-check and by mapping the unique-index violation for the race case.
Learn: check-then-insert is for the friendly message and the unique index is for the truth, so map both to the same answer; `SELECT ... FOR UPDATE` on the parent row serialises structural edits; an absolute "set to N" matches how people count, as long as the server records the delta.

### 10.3 — orders and customers
`GET /admin/orders` filters by status and searches order number or email, newest first and paginated, with the unit count from one grouped query. The detail endpoint returns the order, its payment (with the Stripe payment intent id), the customer, the complete history and `allowedNext`, which is the state machine's list of requestable moves, so the web renders exactly those buttons. `POST /admin/orders/:number/transition` calls the same `transitionOrder` as everything else, so a cancel of a paid order refunds in Stripe, restocks and records `admin:<email>`, and a move to `shipped` queues the shipped email. `GET /admin/customers` lists customers with their placed-order count, selecting only safe columns.
Learn: when the UI offers only what the server says is allowed, the 409 becomes a safety net instead of a user-facing error; selecting named columns is a cheap guard against ever leaking a hash; an admin endpoint should reuse the domain function, not re-implement it.

## Phase 8 (web) — Checkout

### 8.8 — checkout page
`/checkout` is one page with three sections: contact and address (the shared Zod schema checks it, a signed-in shopper gets it pre-filled from their default address and a "save this address" box, a guest gets a sign-in hint), shipping method (the server's quotes for this cart and country, cheapest preselected) and payment. Only the active section is open; finished ones collapse to a summary with an Edit button. "Continue to payment" calls `POST /checkout`, and the Stripe Payment Element mounts with the returned client secret; the Pay button says "Pay €X" with the server's total, and the sidebar never adds money up itself. With no `VITE_STRIPE_PUBLISHABLE_KEY` the payment step says payments are not configured and no order is created, so a fresh clone neither crashes nor holds stock for nothing.

### 8.9 — confirmation page
`/checkout/confirmation/:number` asks the status endpoint every two seconds until the order stops being `pending_payment`, for at most 30 seconds. It shows "Confirming your payment…", then "Thank you, your order is paid!" with the items, totals, address and method read from the order endpoint, or "we are still confirming, you will get an email" after the timeout; a failed payment offers another try and a cancelled order says so. If the very first answer takes more than four seconds it explains that the free server is waking up. `purchase` is tracked once per order, and the cart badge is refreshed when the order is paid.
Learn: the page can only report what the webhook decided, so it waits instead of trusting the card form; polling needs a deadline; an analytics event that carries money must be guarded against reloads.

### 8.10 — e2e payment flow
There are two checkout tests. The real one types the 4242 card into Stripe's iframe and waits for the webhook that `stripe listen` forwards; it skips itself with a loud message until the three Stripe keys are in `.env`, so it has been written but not run. The simulated one always runs: it walks the UI through address and shipping to the payment step, places the order with the same API call the UI makes, pays it with `POST /test/webhooks/simulate`, and checks that the open confirmation page flips from pending to paid without a reload, the cart is empty and the stock fell by exactly the quantity bought. For that to work without a Stripe account the API boots a fake payment gateway when `NODE_ENV=test` and no key is set (never in development or production), and the e2e suite now starts its own test-mode servers on ports 3100 and 5273.
Learn: a test double belongs at the one seam the code already has (the gateway) and should be switchable only where the matching test-only route already is; checking stock through `available` shows a reservation turning into a decrement, which a status check alone would not.

### 11.1 — coverage review
`pnpm coverage` runs Vitest with the v8 provider in every package (config lives next to each Vitest config; the API excludes only tests, helpers, the entry point and the migrate/seed/reset scripts, plus the Drizzle table declarations). ### 11.4 — quality gates in CI

### 11.5 — load sanity

Learn: a seq scan is not a bug, it is the planner choosing the cheapest plan for a small table; read `actual time` and row counts before adding an index, and measure on data the size you expect.

## Phase 14 — Catalogue depth

### 14.1 — schema: brands, collections, tags, variant fields
New tables: `brands`, `collections` + `collection_products` (ordered many-to-many through a `position` column), `tags` + `product_tags`, and `trial_redemptions`. `products` gains `brand_id` (nullable, `ON DELETE SET NULL`), `is_eco`, `is_bestseller_override` and `badge_new_until`; variants gain `net_amount`/`net_unit` (grams or ml, integers), `is_trial` and `swatch_hex`. Constraints carry the rules: a unique slug on each public thing, a collection window must end after it starts, a net amount needs a unit and vice versa, and swatches must match `#RRGGBB`. The migration also copies the old `attributes.brand` text into `brands` rows and `brand_id`, then removes the jsonb key, and a test re-runs that data step on a product that still has the old shape. The trial table's unique index is partial (live rows only), so a cancelled order can release a slot without deleting history.
Learn: put facts you filter, count or give a page to in real tables with foreign keys; keep jsonb for loose, niche attributes. A partial unique index enforces "at most one live row" in the database, which no service-level check can guarantee under concurrent requests.

### 14.2 — pure helpers: unit price, badges
Everything here lives in `packages/shared` so the API (which sorts and filters) and the web (which prints) can never disagree. Unit price is `round_half_up(priceCents * 1000 / netAmount)` done with integers as `floor((2a + b) / (2b))`, which avoids the float error in `x.5` cases, and returns `null` for anything without a usable net amount. `isPaidOrLater` is written as an exclusion (not pending, not cancelled) so statuses added by later phases count automatically, and the label table is a full `Record<OrderStatus, string>` so a new status will not compile until it has wording. Badges are derived: New (under 30 days or before `badge_new_until`), Sale, Low stock (default variant only), Eco and Bestseller (manual override or top 10% by recent units, ties included).
Learn: store only what cannot be computed; a derived value has no way to go stale. And when you round, write the rule down and test the exact-half cases, because those are where implementations differ.

### 14.3 — seed: reptiles, brands, tags, collections
The seed is now a typed pipeline: one file per area (`brands.ts`, `tags.ts`, `collections.ts`, one `products-<pet>.ts` per pet), a Zod `SeedProductSchema` plus cross-checks (known brand, tag, category, collection) that run before any insert, and `ON CONFLICT (slug) DO UPDATE` everywhere so running it twice changes nothing. Members of the Eco Picks and Under €10 collections are computed from product data, so they cannot go stale when a price changes; themed ones are listed on the product. Seasonal windows are recomputed at seed time from a yearly month/day range. New brand names were searched on the web first and two suggestions were dropped as too close to real brands.
Learn: validating input at the edge of a pipeline turns a typo into an error that names the product, instead of a broken card in the UI; and an idempotent upsert needs a natural unique key (slug), not a generated id.

### 14.4 — catalogue growth to 125 products and the image pipeline
Every one of the 31 leaf categories now has at least five products (a test counts per leaf and fails below five), which takes the shop to 125 products and 451 variants across six pets. Fifteen food and treat products carry a trial size as a third value of their pack axis, and every colour variant carries a `swatch_hex` from one palette in the seed. The product lists were written as a compact table and turned into typed seed files, then checked by the Zod schema and tests for unique slugs, unique SKU codes, positive integer prices and swatches. Images follow the pipeline: `docs/images-brief.csv` is generated from the seed (slug, shot, prompt, shared style suffix, raw file), and any product without a processed photo shows its pet's placeholder until the real image is generated, processed and the seed re-run.
Learn: a "minimum per group" rule belongs in a test that counts, because growing a catalogue by hand always leaves one group short; and a fallback (placeholder) is better than a missing-file error, because the page is correct at every stage of the pipeline.

### 14.5 — catalog API: brands, collections, tags, derived fields
`GET /products` gained `brand`, `tag`, `collection` and `badge` filters and the `unit_price_asc` sort. Brand and tag are plain SQL (`IN` on the brands table, `EXISTS` on the join table); the collection filter reuses the "live now" condition; the unit price is computed in SQL on the default variant with the same integer rule as the shared helper (cast to bigint so price times 1000 cannot overflow) and sorted `NULLS LAST`. Badges are derived in code for the whole catalogue from one cached index, so the filter, the facet and the card all agree. Cards add `badges`, `unitPrice`, `brand` and per-colour `swatches`; facets add brand, tag and badge counts over the same scope, ignoring the filter just clicked. The detail response adds brand, tags, badges and each variant's unit price and trial flag.
Learn: a sort key that is computed (unit price) must be computed in SQL, or paging breaks; and a rule that exists in code and in SQL will drift, so keep one and feed the other its result.

### 14.6 — API: brand and collection endpoints (public + admin)
Public `GET /brands`, `/brands/:slug`, `/collections`, `/collections/:slug` and `/tags` are cacheable and cookie-free, mounted before the session middleware. A collection is live when it is switched on and now is inside its window (either end may be open); outside that it is a 404, indistinguishable from a missing one, and the product filter uses the same rule so it cannot leak a hidden collection. The admin side (behind `requireAdmin`, audit-logged) does CRUD on brands, collections and tags, saves a collection's products as one ordered list (the whole list replaces the old one, which is how reordering is saved), sets a product's tags, and lets a product's brand, eco flag, bestseller override and new-until date be edited. Slugs are fixed after creation, a duplicate is a 409 (also when two admins race, via the unique-violation mapping), and a window that ends before it starts is a 400 before the database check ever fires.
Learn: authorisation belongs in one `router.use` on the prefix so a new route is protected by default; and when a business rule has to live in both code and SQL, test the two against each other.

### 14.7 — trial sizes: one per customer
The rule is "one unit of each trial variant per customer, ever", and it is checked three times because each layer fails differently: the cart refuses a second add or a quantity of 2 (`409 TRIAL_LIMIT`, early and friendly), checkout re-checks from the database with the customer key (user id, or the lower-cased email for a guest) so editing the cart some other way cannot bypass it, and a unique partial index on live `(customer_key, variant_id)` rows holds even when two checkouts race. A redemption is written when the order is paid and released (not deleted) when it is cancelled. That needed a way to react to an order changing without editing the order code each time, so `orders/events.ts` is a small typed in-process registry (`onOrderPaid`, `onOrderCancelled`, `onOrderRefunded`) that `applyTransition` emits to inside its transaction; later phases (points, referrals, store stock) subscribe instead.
Learn: enforce a business rule where it is cheap (UX), where it is authoritative (service) and where it is unbreakable (database); and an in-process event registry is enough when there is one process and the handlers must commit with the change.

### 14.8 — web: cards, PDP, filters, sort
Cards now carry the server's derived badges (never stock numbers), a unit price line (`€4.20/kg`, with one footnote per list saying it is rounded to the nearest cent) and colour dots. The dots are buttons, so they live below the product link rather than inside it; hovering or focusing one previews that colour's photo and clicking (a tap on a phone) keeps it, and past four colours the rest become "+N colours". The product page shows the selected variant's unit price, the badges, a "Trial size" pill with the one-per-customer note, and surfaces the server's `TRIAL_LIMIT` message when a second sample is refused. The list gains Brand and "Shop by health need" groups, a "Lowest unit price" sort and named filter chips, all stored in the URL (`brand=`, `tag=`, `sort=unit_price_asc`) through the same `list-params.ts` that already owned the other filters, and the collection page (next step) reuses the listing through a `collection` prop.
Learn: interactive children of a link are a bug, so restructure the card instead of stopping click propagation; and keeping every filter in the URL means a new filter is a few lines in one parser rather than new state.

### 14.9 — web: brand and collection pages, admin screens
`/brands` lists the brands, `/brands/:slug` shows the story above the usual listing with the brand fixed (and its facet hidden, since other brands would be a trap), and `/collections/:slug` does the same for a collection with an "Until 2 November" line for seasonal ones; each has `<Seo>`, a `track()` event and a proper not-found state (a finished season is a 404, because the API says so). Reptiles join the pet nav through the typed `PETS` list, with their own accent and glyph, and Brands is linked from the header, the drawer and the footer. `SeasonalCollectionSlot` is exported for phase 20's homepage registry and renders nothing when no seasonal collection is live. The back office gains Brands, Collections and Tags screens plus a "Brand, badges and health needs" block on the product page; collections are ordered with up/down buttons and saved as one list.
Learn: a page that is "one listing with one fixed filter" should be the same listing component with a prop, not a copy; and an accessible name made of a visible word plus a visually hidden one needs a real space between them, which a test that asks for the exact name catches.

### 14.10 — e2e
One new spec drives the whole phase through the browser: on the dog page it ticks Burrow & Biscuit and "Dental care" (both land in the URL and as named chips, leaving two products), sorts by "Lowest unit price" and checks the unit prices on the cards ascend, opens the Puppy Starter Kit collection and then Soft Training Bites, picks the trial size (pill and "one per customer" note appear), adds it once and sees the second add refused with the cart still holding one unit. Smaller tests check the brands page and a brand page, the not-found pages for an unknown brand and collection, and that Reptiles are reachable and themed. Running the whole suite found three older tests broken by the bigger catalogue (a folded filter group, and two that relied on which variants the random stock sequence happened to leave sold out or low); the seed now pins those two facts on purpose.

## Phase 20 — Content & trust

### 20.1 — content tables and Markdown seed pipeline
Guides and help articles are written as Markdown files in `apps/api/content/` and seeded into Postgres, so the same text can be edited in the admin, linked to products and searched. Front matter is checked with a strict Zod schema (an unknown key, a missing field, a bad date, a slug that differs from the file name or an unknown product slug all stop the seed with the file name in the message), and rows are upserted by slug so seeding twice changes nothing. `help_articles.search` is a generated `tsvector` column (question weighted A, answer B) with a GIN index, so the database keeps the search index fresh on every edit. The test database name must end in `_test`: the safety net in `global-setup.ts` refuses anything else.
Learn: a `GENERATED ... STORED` column needs an immutable expression, which is why the text-search configuration is the literal `'english'` and not a setting; and failing the seed on one bad file is better than half-publishing content.

### 20.2 — pet-care guides (API and web)
`GET /guides`, `/guides/:slug` and `/guide-categories` are public and cached like the catalog. "Visible" is one rule used by every query: published AND past its publish date, so a draft and a scheduled guide are both a plain 404 from outside. Related guides are one ordered query (same category first, then newest, never the guide itself), which tops a small category up instead of showing a short list. Linked products reuse the catalog's own card query (a new `ids` filter), so a guide card can never disagree with the product grid about price or stock, and an archived product is simply not recommended. The web renders the Markdown with `react-markdown`, which builds React elements and ignores raw HTML, so no `<script>` or `onerror` can come from content; the test proves it.
Learn: sanitising by construction (never turning text into HTML) beats sanitising by filter; and a reading time is words divided by about 200 per minute, rounded up, computed in SQL so the list does not ship every body.

### 20.3 — help centre with search
Search is Postgres full-text: `websearch_to_tsquery` turns whatever a visitor typed into a query and never raises a syntax error, so quotes, `&`, `:*` or `'; drop table` are only text (and the value is always a bound parameter). The generated column weights the question (A) above the answer (B), so `ts_rank` puts a title match first with no extra code. `ts_headline` builds the snippet only for the at most 30 matching rows, and marks matches with two private-use characters instead of `<b>` so the web renders `<mark>` itself and answer text can never inject markup. A query of only stop words ("the") compiles to an empty tsquery, so it falls back to a substring match. `searchHelp(q, topic)` (API service) and `searchHelp({ q, topic })` (web client) are the names phase 24 calls.
Learn: ranking weights belong in the index definition, not in the query; and the URL (`?q=&topic=`) is the state, with a 300 ms debounce so typing does not create a request and a history entry per keystroke.

### 20.4 — public order tracking
Tracking without an account proves ownership with two facts, the order number and the email, checked in ONE query (`orders.email` is `citext`, so case never matters). Because "no such order" and "wrong email" are the same `undefined`, the route throws one `NOT_FOUND` with one fixed message: the two bodies are equal byte for byte, and even a malformed pair gets the same 404 (the schema is deliberately loose, so a 400 never reveals what an order number looks like). The response is a whitelist built field by field (status, item names and quantities, timeline), so address, totals, payment ids and the admin's history notes cannot leak by accident, and a test searches the JSON for them. The route is POST (the email must not sit in a URL or a log) and limited to 10 an hour per IP. Phase 14's `ORDER_STATUS_LABELS` and phase 22's shipment data plug into `modules/tracking/status-labels.ts`.
Learn: enumeration defence means equal answers, equal status, equal cost; and rate limits matter most on endpoints that answer yes or no about a secret.

### 20.5 — footer, legal pages, withdrawal form and cookie notice
The footer is data (five groups, one click handler per group that reports `footer_link` with the group and label), and the seven static pages are one `LegalPage` component over Markdown files, so the "demo store, fictional company, not legal advice" line lives in the frame and cannot be lost when the copy is rewritten. A withdrawal reuses the order-tracking ownership check and its identical 404; the row and its acknowledgement email commit in one transaction through the outbox, and the email states the exact UTC time of receipt, which is what a "durable medium" confirmation is for. To make that possible the outbox grew a nullable `order_id` and a JSON `payload` (data, not rendered HTML, so a template fix still reaches queued mail). The cookie notice says only what is true, and `consent.ts` answers `hasConsent(category)` with false for everything optional, so a later analytics phase has to ask and nothing can load "by default"; the record sits in `localStorage` because remembering the notice must not need a cookie.
Learn: strictly necessary cookies (session, cart) are exempt from consent under the EU rules, but analytics and marketing are not, so the safe design is a function every optional script must call first; and an acknowledgement email earns its legal weight from the timestamp it carries.

### 20.5b — contact form (added by the lead)
The legal and help copy points customers at `/contact`, so the form was added after 20.5. `POST /contact` stores the message and queues two emails (a copy to the customer, a notification to the shop's `SHOP_INBOX_EMAIL`) in the same transaction, so a stored message always has its mail and a mailed message is always stored. The spam defence is layered and cheap: a rate limit (5 an hour per IP), a honeypot field that humans cannot see or reach with the keyboard (a bot that fills every input fills it, and the API then answers a normal-looking 201 while storing and sending nothing, so the bot learns nothing), and Zod limits on every field. Visitor text is always escaped in the HTML emails. The form validates with the same shared schema as the API, shows an error under each field wired with `aria-describedby`, and moves focus to the first bad field.
Learn: a honeypot must fail silently (an error message teaches the bot to skip it); and writing the row and the outbox entries in one transaction is what makes "we got your message" true.

### 20.6 — product safety notices
A notice is data with one definition of "active" (published, started, not ended) used by every public read, so an expired recall leaves the homepage and the product pages with no cleanup job; a CHECK keeps `ends_at` after `starts_at`. Notices attach to variants, not products (a recall is often one size or batch), and the product detail gains `safetyNotices[]` looked up through those variants. `role="alert"` interrupts a screen reader, so only a recall gets it; the severity is also written as a word so colour is never the only signal. Emailing past buyers is idempotent by construction: `safety_notice_deliveries` has a unique `(notice, email)`, `INSERT ... ON CONFLICT DO NOTHING RETURNING` yields only the emails that were not there, and exactly those are queued, in the same transaction, so a double click or a retry sends nothing twice and a later run reaches only new buyers. Guest orders count because the email lives on the order itself.
Learn: let a unique constraint be the idempotency key instead of a read-then-write check (which races); and put the dismissal in `sessionStorage` when the message should come back tomorrow.

### 20.7 — richer homepage
The homepage is now a list of sections, and the page itself stays small. One call, `GET /home`, returns the hero slides, the promo tile and the bestsellers; the bestsellers come from the same badge index the product cards use (sales-derived or the editorial override), topped up with the newest products when a young shop has fewer than four, so the section is never half empty. A promo that is switched on but has no text is sent as `null`, so the web never re-checks. Caching follows the rest of the public API: the router stamps the 60 s public cache header. The carousel owns a fixed-height box (the loading skeleton uses the same classes), so neither loading nor changing slides moves the page, which is what the layout-shift score measures. It starts paused for `prefers-reduced-motion`, pauses while hovered or focused, announces changes politely only when paused (a live region that talks every six seconds is noise), and uses real buttons for previous, next, play/pause and the dots. Later phases plug in through `features/home/slots.ts`: a fixed list of ids, a `register` call, and nothing else; the order comes from the list, not from who registered first, and a slot that renders nothing leaves no gap because its wrapper is `empty:hidden` (the margin goes with it).
Learn: reserve space for anything that arrives late (a fixed box beats a guessed one); and make extension points data (an ordered id list) instead of editing a shared file, so merges and import order cannot reorder the page.

### 20.8 — admin content management
Every content type gets the same four moves: a list, a form that submits the whole document (PUT replace semantics, because editors send whole forms), a Zod schema shared with the API, and an audit line. The Markdown editor is a textarea next to a preview that renders with the storefront's own `MarkdownBody`, so "what you see" is the real output and raw HTML never renders there either. A guide's category is a name that is created on first use, its linked products are replaced as a set inside the save transaction, and publishing without a date means "now" while a draft keeps its old date (so unpublishing and republishing does not rewrite history). Withdrawals keep their first `acknowledged_at` even if someone moves a request back. Safety notices attach to variants through a small search-then-pick control, and the notify button shows the delivery count and the server's honest answer ("queued 2, 3 already emailed"). Hero slides and the promo tile are two JSON rows in `home_content`, validated per key, with defaults used when a row is missing or no longer matches its schema.
Learn: validate a stored JSON document on the way out as well as on the way in (an old shape after a deploy must fall back, not break the homepage); and keep admin forms honest by showing server messages instead of a generic failure.

### 20.9 — e2e
One spec, `e2e/content.spec.ts`, walks the phase's public features as a visitor would: the hero carousel (pause, next, previous), a guide opened from the list with a click on a linked product, a help-centre search (a hit, then a nonsense query that offers "Contact us"), order tracking (wrong email and unknown number get the very same words, the right pair shows the order), a withdrawal (reference `WD-xxxxxxxx` appears) and the cookie notice (shows, does not block the page, gone after OK and after a reload). The seed creates no orders on purpose, so the two tests that need one place and pay for their own through the checkout API and the test-only payment simulator, each with a unique email, buying a product no other spec buys so stock checks elsewhere stay exact. Writing the carousel test found a real bug: the slide wrapper had `grid` and the `hidden` attribute, and the class beat the attribute, so every slide was always laid out (the first one stayed on top and "next" changed nothing visible). The fix is one variant, `[&[hidden]]:hidden`.
Learn: a Tailwind display class (`grid`, `flex`) overrides the browser's `hidden` attribute, so pair them with an explicit hidden variant; and a test that asserts what the visitor can see (exactly one slide visible) catches what unit tests on attributes miss.

## Phase 18

### Step 18.1 — pure pricing engine
- `priceCart(input) -> PricedCart` lives in `packages/shared/src/pricing/`. It takes `now` as an input instead of reading a clock, and it does no I/O. Same input, same output, so a unit test can cover every rule.
- The stacking order is fixed: best single line price, then tier OR code (whichever saves more), then shipping. Prices never stack with each other, and a code never stacks with a tier. Ties go to the tier because the customer gets it without typing anything.
- Order-level discounts are split across lines with largest-remainder allocation: floor each share, then hand the leftover cents to the biggest fractional remainders (ties: earlier line). Line sums then equal the adjustment exactly, which is what refunds need (`order_items.discount_cents`).
- Percent rounds half-up on cents via `applyPercent`. Example: 10% of 99 is 9.9, so 10 cents, split as 4, 3, 3 over three 33-cent lines.
- `fixedPrice` lines (trial sizes, bundles) are modelled as a plain boolean input. They skip tiers and codes but count towards shipping and gift thresholds.

### Step 18.2 — gifts, progress, credits, notices
- Thresholds (gift, free shipping) use the merchandise total after the order discount and BEFORE credits, so paying with points never costs a customer their gift or free shipping.
- Credits go last, each capped at what is left of the merchandise (never shipping) and allocated to lines like any other adjustment, so the line column stays the single source of truth for refunds.
- Progress bars are data (`thresholdCents`, `remainingCents`, `percent`, `reached`); the UI only draws them. Percent is floored so 99.9% never shows as 100%.
- Notices are machine keys (`code_not_stackable`, `code_min_spend`, ...), the UI turns them into kind sentences.

### Step 18.3 — promotions schema and seed
- Eight tables in one migration (`0013_promotions`): `discount_codes`, `discount_redemptions`, `bulk_tiers`, `gift_rules`, `flash_sales`, `flash_sale_items`, `price_history`, `order_promotions`; plus `product_variants.member_price_cents` and `order_items.discount_cents`.
- The database guards the rules the engine assumes: a percent code is 1..100, a fixed code is above 0, a free-shipping code has no value, windows end after they start, one tier per threshold, one active gift rule (partial unique index), one redemption per code per order, a line discount never above its line total.
- Codes are `citext`, so `paws10` finds `PAWS10`. Redemptions are released, never deleted (same idea as trial redemptions), so the usage cap only counts live rows and history stays.
- `order_promotions` copies type, label and cents as values and keeps the rule id as text, not a foreign key: editing or deleting a code later must not rewrite what an old order says.
- Seed: PAWS10 (10%, min EUR 30, not on sale items), WELCOME5 (EUR 5, first order, once per customer), FREESHIP (min EUR 25), tiers 5% over EUR 75 and 10% over EUR 100, a free bag of Peanut Crunch Biscuits from EUR 40. Idempotent: codes and tiers upsert on their natural key.

### Step 18.4 — discount codes and the priced cart
- `GET /cart` (and every cart mutation) now carries `pricing`: the engine's adjustments, discount, gift, progress bars and notices. Shipping in the cart is an estimate with standard delivery; checkout prices the method actually chosen.
- The promotions service only loads rules and calls `priceCart`; it adds the checks that need the database (unknown or archived code, global cap, per-customer cap) as notices of its own. Usage caps count live (unreleased) redemptions only.
- `POST /cart/code` stores the code on the cart, re-prices, and refuses with one kind sentence ("Add EUR 15.00 more to use this code", "This code expired on 12 Oct", "You've already used this code") if the code would do nothing. A code the bulk tier beats is kept, with a `code_not_stackable` notice, because adding more items can still change which one wins.
- The cart stores the code as text, not a foreign key: it is looked up again on every pricing, so an archived or edited code is never trusted from the moment it was applied (and it avoids a carts → promotions → orders → carts import cycle).
- A guest's per-customer and first-order history is unknown until checkout asks for the email, so the cart accepts the code and checkout repeats the check with the email.

### Step 18.5 — checkout priced by the engine
- `placeOrder` now asks the engine for every amount, with the method actually chosen and the customer's email, inside the same transaction that reserves stock. Subtotal, discount, shipping and total on the order are the engine's; the PaymentIntent amount is the order total, as before.
- Each order line stores its share of the order discount (`discount_cents`, largest-remainder split): the column refunds will read. `order_promotions` copies what was applied as values, so editing PAWS10 tomorrow does not change today's order.
- The cap race: the code row is locked `FOR UPDATE` before its live redemptions are counted, and the redemption is written in the same transaction. Two checkouts for the last use queue on that lock; the second one counts the first one's row and is refused. Lock order is cart → inventory (variant-id order, the gift's row included) → code, the same in every checkout, so no deadlock.
- Re-placing the same pending order (a second "pay" click) leaves its own earlier redemption out of the count, so a one-use code does not refuse its own retry.
- The free gift is a zero-priced order line with one unit reserved. It is reserved last: if this cart's own lines took the final unit, the order just has no gift (it costs nothing, so no amount changes).
- A cancelled order that was never paid releases its redemption (an order-events subscriber, in the cancel transaction); a paid-then-cancelled order keeps it, because the code was consumed.
- Shipping quotes now use the merchandise after discounts for the free-delivery threshold, like the engine, so the quote and the order agree.

### Step 18.6 — flash sales and Omnibus price history
- `price_history` is append-only and gets a row at every price event: the seed (one `base` row per variant without history, backdated 60 days, idempotent), creating a variant, every admin change of `price_cents` (same transaction as the change) and a sale's activation (one `sale` row per item at the sale's `starts_at`). No migration: 0013 already had the tables.
- `syncFlashSales(run, now)` stands in for the phase 19 job and is called at the start of cart loads, catalog list/detail reads and the banner. `UPDATE ... RETURNING` flips a sale once, so with concurrent callers one of them wins the sale and writes its history rows, in one transaction with the flip. A cheap SELECT first means a request with nothing due opens no transaction.
- The Omnibus reference of a sale item is the lowest base or sale price in the 30 days before `starts_at`, counting the price that was already in effect when that window opened (a price set 90 days ago and never changed was charged the whole window). The sale's own row is at `starts_at`, so it can never be its own reference. No history means null, and null means no strike-through anywhere; `compare_at_price_cents` is never used.
- A sale is applied only while status is `active` and `starts_at <= now < ends_at`; the lowest price wins across overlapping sales. `promotions.price()` hands it to the engine as `saleCents` + `onSale`, so cart and checkout charge the same amount and a code that excludes sale items skips the line. Trial sizes keep their fixed price.
- Catalog: cards and detail variants carry `sale` (`priceCents`, `referenceCents`, `basePriceCents`, `endsAt`). The web shows the sale price, the regular price struck through only when there is a reference, and "Lowest price in the last 30 days: EUR x" next to it (`SalePrice`).
- `GET /promotions/banner` (active sale ending soonest, else next scheduled, plus `serverNow`) and `GET /promotions/rules` (tiers, gift threshold, free-delivery threshold of the standard method) are public.

### Step 18.7 — member prices
- No migration: `product_variants.member_price_cents` came with 0013. `promotions.price()` loads member prices (only when a user is signed in) and passes `memberCents`; the engine's rule min(base, sale, member) does the rest, so cart, checkout and the order charge the same amount, and a guest cart is re-priced the moment the login merge makes it a user's cart. Trial sizes stay fixed.
- Catalog: the catalog routes now run `attachUser` (a cookie-less request costs nothing). Payloads carry `hasMemberPrice` always and `member: { priceCents }` only for a signed-in viewer; a guest's JSON has no member number (tested on the raw text). `catalogCache` sends `Vary: Cookie` on every catalog response, `public, max-age=60, stale-while-revalidate=300` to guests and `private, no-store` to signed-in users.
- Web: `MemberPrice` ("Member price EUR x" + muted regular price) and `MemberTeaser` ("Member price: log in to see", link to `/login?next=<current product>`). The member price replaces the sale only when it is lower (`memberBeatsSale`); on a card the teaser sits outside the product link. Login/logout refetch the product queries.
- Admin: `memberPriceCents` on the variant create/update API (must be below the price; null clears it), a `member` history row on set/change, and a "Member price (optional)" field in the variant form (euros parsed to integer cents from the string, no float maths).
- Seed: 8 variants get a member price ~10% below base (integer rounding) and one `member` history row.
- Not done here: the web cart lines still print `items[].unitPriceCents` (catalog price); showing the engine's `pricing.lines[].unitCents` there belongs to the cart UI step (18.9a), which also covers sale prices.
### Step 18.9a — promotions in the cart (UI, first half of 18.9)
- The cart page and mini-cart now render the engine's `pricing`: free-delivery and gift progress bars (`role="progressbar"`, `aria-valuenow/min/max`, the sentence doubles as `aria-valuetext`), itemised adjustments (label and negative amount; a free-delivery adjustment says "Free delivery"), the free gift as a "Free gift" line at EUR 0.00, the delivery estimate and the estimated total. Every figure after the subtotal comes from the API; the browser adds nothing.
- Code box (`CartCode`): the shared `ApplyCodeSchema` checks the shape first, the API's kind sentence appears under the input, an applied code becomes a chip with Remove. `useCartCode` joins the cart's write queue, so it cannot race a quantity change. `track('promo_applied')` / `track('code_failed')`.
- All wording about promotions sits in `promo-text.ts` (notice key to sentence; the stacking order for the native "How discounts combine" `<details>`). The old "Shipping and taxes are worked out at checkout." is replaced by the standard-delivery estimate and "Demo store: no tax is charged."
- Checkout: a 400 with `fieldErrors.code` shows its sentence in the step alert and beside the summary with a way back to the cart.
- Not here (later steps): sale banner and countdown, Omnibus line, member teaser, admin screens, the e2e spec.

### Step 18.8a — admin: discount codes, bulk tiers, gift rule (flash sales and member prices come later)
- API (`modules/promotions/admin-{router,service,repo}.ts`, mounted in the admin router so it sits behind `requireAdmin` + the audit log): `/admin/discount-codes` (list with live-redemption count, create, PUT update, DELETE = archive or delete), `/admin/bulk-tiers` (list, create, PUT, DELETE), `/admin/gift-rule` (GET the active rule or null, PUT set by SKU or id, DELETE switch off). Shared Zod schemas in `packages/shared/src/schemas/admin-promotions.ts` give the sentence before the database check constraints do (percent 1..100, fixed above 0, free shipping 0, end after start, caps above 0 or empty).
- Duplicates are mapped from the unique violation, not only pre-checked, so a race between two admins is a clean 409: a code in any letter case (citext), a second tier on the same threshold, a second active gift rule.
- Web: one "Promotions" nav item, tabs inside. The code form shows a live preview sentence ("10% off, min EUR 30.00, 5 of 100 used"), built by the same `describeCode` the list uses, so the list and the form can never disagree. Euro fields parse the typed string to cents (`inputToCents`), never `Number(x) * 100`. Tables scroll inside their own bordered container; the tab row wraps.
- Tests: API 25 (403/401, duplicate 409 any case, percent 101/0, free shipping with a value, ends before start, overlapping tier on create and on edit, archive-not-delete, audit lines); web 48 (euros to cents edge cases, validation with `aria-describedby`, preview, list, 409 messages, gift on/off).
- Not here: flash sales admin, member price field in the variant form, a product picker for the gift, un-archiving a code.

### Step 18.8b — admin: flash sales

- Web: a "Flash sales" tab in Promotions (no new nav item). A live or ended sale opens read-only, with each item's Omnibus reference ("Lowest 30-day price: EUR x" or "No history"); a live one offers "Move the end" and "End now".

### Step 18.10 — e2e
`e2e/promotions.spec.ts` has five tests. (1) One Cuddle Cup Bed (EUR 37.90) in the cart: the gift bar says "Spend EUR 2.10 more for a free gift" (the seeded bed is 10 cents off the plan's EUR 38 round number), then a EUR 6.99 chew stick makes the bar say "You get a free gift!" and the free Peanut Crunch Biscuits line appears at EUR 0.00. (2) PAWS10 on two beds (EUR 75.80): the code saves 7.58 against the 5% tier's 3.79, so the code wins; a third bed (EUR 113.70) makes both save 11.37, the tie goes to the tier, the notice says "saves more than PAWS10, so we used that" and the "How discounts combine" panel explains the order. (3) An admin schedules a flash sale through Promotions > Flash sales with a start ten minutes in the past, so it is live on the first read; a fresh browser context sees the banner, the sale price and "Lowest price in the last 30 days: EUR 37.90" on the product page and in the cart. (4) Three beds are bought with the simulated gateway and the admin order detail lists the order's promotions. (5) A guest sees "Member price: log in to see", the link goes to `/login?next=...`, and after signing in as the seeded customer the page shows "Member price EUR 5.39".
The admin order detail did not show `order_promotions` and no endpoint exposed them, so this step added `promotions` (type, label, cents) to `GET /admin/orders/:number` and a "Promotions applied" list under the totals in the admin order page. Isolation: the flash sale sits on a product no other spec uses, has a unique name, and is ended (or deleted if still scheduled) in `finally`; the Omnibus reference is asserted as a range (EUR 29.90 to 37.90) because on a re-run an earlier run's ended sale is inside the 30-day window and the rule counts it; a sale left by a crashed run is cleaned up at the start of the test. Only test (4) buys, and only a bed nothing else buys.
Learn: a test that sets up server state through the UI must also undo it, or the next spec (running in parallel on the same database) sees a banner and sale prices it never asked for; and two rules that tie (10% tier against a 10% code) are the test that pins down which one the product promises.

## Phase 15 — Discovery & navigation

### 15.1 — pet profiles: API
- Table `pets` (migration `0015_pets`): `user_id`, `name`, `species` (a Postgres enum built from the shared `PET_VALUES`, so a profile can never name a pet the catalogue has no products for), `birthday` as a plain `date`, `approx_age_months`, `size`, plus the usual `updated_at` trigger. The birthday is a calendar date with no time zone because "born on 18 March" must be the same everywhere, and phase 19 will email on it; Drizzle returns it as the string `YYYY-MM-DD`, so nothing shifts it by a time zone.
- `GET/POST /account/pets`, `PATCH/DELETE /account/pets/:id`, `POST /account/pets/merge`. Every query filters by pet id AND owner, so someone else's pet looks like a missing one (404, same as addresses). The limit of 8 is a count-then-insert, so each write first locks the user row; a test fires eleven parallel creates and exactly eight succeed.
- The merge takes the guest's local pets after sign-in, skips any whose name (case-insensitive) and species the account already has, adds the rest until the limit, and returns the final list. It never fails for "too many": it keeps what fits.
- `packages/shared/src/pet-profiles.ts` holds the pure part: `AGE_STAGES` (one table of thresholds in months per species), `petAgeMonths` (the birthday wins over the rough age), `ageStageFor` and `petToFilters(pet, now)`. A dog is a puppy under 12 months and a senior from 96, a cat a kitten under 12 and a senior from 132, small pets are seniors from 48, and birds, fish and reptiles have no stages. The age stage filter always includes `all`, because two thirds of the catalogue carries that value and "adult dog" would otherwise hide most of it.
- Learn / explain: why a birthday is a `date` and not a timestamp (a timestamp has a time zone, a birthday does not); why `now` is an argument (the thresholds become unit-testable and the same code runs in the browser for guest pets).

### 15.2 — pet profiles: web
- `features/pets/` holds one hook, `usePets()`, that hides where pets live: a signed-in user's come from the API (TanStack Query), a guest's from `localStorage` through a tiny external store (`guest-store.ts`, read with `useSyncExternalStore`, same array until something changes). Every storage access is in try/catch and the store falls back to memory, so a blocked browser still works for the visit. The page, the header switcher and the shop filters therefore behave identically for both. `/account/pets` is deliberately a public route (listed before the guarded `account/*` splat), because a guest has to be able to add "Biscuit".
- "Who are we shopping for" (`ActivePetProvider`) is a per-visitor choice stored in the same store, for guests and accounts alike. If the stored id matches no pet any more (deleted on another device) the shopper is simply shopping for everyone. The header pill "Shopping for Biscuit" is a disclosure (button with `aria-expanded`, Escape returns focus), not a `role=menu`: the panel holds ordinary buttons and links, and a menu role would promise arrow-key behaviour we do not have. The mobile drawer lists the same choices.
- The active pet is the DEFAULT of a list, not a lock. `usePetDefaults` writes `petToFilters(pet)` into the URL (`attr.pet=dog&attr.ageStage=adult,all`, replacing the history entry) when a search page or a category page of the pet's own species opens without pet filters of its own. The URL then says what the shopper sees, a shared link works for someone with no pet, `?pet=<id>` never appears, and the first request already carries the filters (the listing holds it back until the URL is written). Filters we did not write (a shared link) are never overwritten; ours are replaced when the pet changes. A one-line note "Showing what suits Biscuit. Show all pets" clears it in one click, and removing chips by hand also sticks, because the "already applied" memory is kept per page and pet for as long as the list is mounted.
- On login or registration `mergeGuestPets` sends the browser's pets once to `POST /account/pets/merge`, drops the local copy, re-points the active choice at the same-named pet (its local id no longer exists) and refetches. If the call fails the local pets stay and the next sign-in tries again.
- `track('pet_added' | 'pet_activated')` fire with the species only (never the name).
- Learn / explain: why a hook can hide "server or browser" (the components above it never branch); why `useSyncExternalStore` needs a stable snapshot (a new array each call is "changed", so React would loop); why the merge uses the server's answer instead of guessing the final list.

### 15.3 — filters: price slider, in-stock, quick chips
- The API already answered `minPrice`, `maxPrice`, `inStock` and returned the price range of the scope as `facets.price` (min and max cents, counted over the scope and not over the price filter, so the slider's ends do not shrink while you drag). This step adds one thing to the response: `chips`, the quick-filter list, built by the pure `buildQuickChips(facets)` in `packages/shared`: On sale, New, the three biggest brands, the three biggest health needs, so at most eight, and only values with products in the current scope (a chip never leads to an empty list). No new endpoint.
- `PriceSlider` is two native `<input type=range>` stacked on one track (CSS in `globals.css` lets only the thumbs take the pointer). Native inputs give arrow, Home, End and PageUp/PageDown keys and screen-reader announcements for free; each has `aria-valuetext` with `formatMoney`. Steps are 100 cents. The handles cannot cross (the min handle stops at the max one), so "min above max" cannot exist, and a handle resting on its end means no limit (the parameter is removed). While dragging only local state changes; the URL is written on pointer release, on blur, or half a second after the last key press, so a drag is one history entry and one request. This replaced the two text boxes, and the "In stock only" checkbox became a `role=switch` (same input, announced as an on/off setting).
- `QuickChips` is a row of toggle buttons (`aria-pressed`) above the grid; pressing one writes `badge`, `brand` or `tag` to the URL (the list parameter code gained `badge`). Active filters still show as removable chips with "Clear all". On a brand page the brand chips are left out, because the brand is the page.
- Learn / explain: URL as state again, now with six filter kinds: every control writes the URL and reads it back, so load-with-params, change, and reload are the same code path (tests cover the round trip); why commit on release (a drag would otherwise be dozens of requests and history entries).

### 15.4 — search suggest: API
- `GET /search/suggest?q=` answers `{ products[5], categories[3], brands[3] }` with the least data that can fill a dropdown: name, slug, a thumbnail, and the "from" price in cents for products; name, slug and parent name for categories; name and slug for brands. It is public, limited to 60 requests a minute per IP, and answers `Cache-Control: public, max-age=30`. Under two characters is a 400 (the web does not even ask).
- Matching uses three conditions in one query: `ILIKE '%q%'` (served by the new trigram index), trigram similarity (`name % q`, so "hedgehok" still finds "Hedgehog Hideaway"), and the existing `tsvector` (so a word that only appears in the description still finds the product, just lower). The order is a `CASE`: name starts with the input, then a word in the name starts with it, then a substring, then fuzzy and description hits; ties break by trigram similarity, name and id so the order is stable. `%` and `_` typed by the shopper are escaped, so "100%" means the characters.
- Only products a shopper could buy are suggested: active, with an active non-trial variant (the list's own `variantSummary`, now exported). Drafts, archived products and products with no buyable variant never appear. The response is built for everyone alike (list price, no member price, no cookie, no `Vary: Cookie`), which is exactly what makes a public cache safe.
- Migration `0016_search_trigram`: `CREATE EXTENSION IF NOT EXISTS pg_trgm` (written by hand above the generated indexes, because they need it) and GIN `gin_trgm_ops` indexes on `products.name`, `brands.name` and `categories.name`. `pg_trgm` is a Postgres contrib extension and is available on Neon's free tier.
- Learn / explain: why a prefix search needs a trigram (or `text_pattern_ops`) index and an ordinary B-tree cannot serve `ILIKE '%x%'`; why an endpoint that is identical for every viewer can be cached publicly, and why it must not read the session to stay that way.

### 15.5 — search autocomplete UI
- `SearchCombobox` replaces the header search box (and the one in the mobile drawer; `SearchBox.tsx` now just re-exports it, so the layout did not change). It follows the WAI-ARIA 1.2 "editable combobox with list autocomplete": the input has `role=combobox`, `aria-expanded`, `aria-controls` and `aria-autocomplete=list`; DOM focus never leaves the input and the highlighted option is `aria-activedescendant`. The popup is a `listbox` of `group`s (Products, Categories, Brands, or Recent searches) of `option`s. Keys: Down and Up walk the options and wrap, Home and End jump when one is highlighted (otherwise they move the caret as usual), Enter opens the highlighted option or, with none, runs the plain search (`/search?q=`), Escape closes the list and a second Escape clears the text, Delete forgets a highlighted recent search.
- A polite live region says what arrived ("5 products, 2 brands", "No suggestions", "Searching") and is always in the DOM, so the first announcement is not lost.
- Debounce 200 ms (`useDebounced`: the timer lives in an effect, cleanup cancels it) and cancellation: the query key is the settled term, `enabled` only while the list is open and the term has two characters, and TanStack Query passes `signal` to `fetch`, so a request for a term the shopper has typed past is aborted. Nothing stale is ever shown for newer text: the list is only drawn when the settled term equals the trimmed text.
- Recent searches (the last 6, newest first, case-insensitive duplicates merged) live only in `localStorage` (`pawsome.recentSearches`), are shown on focus with an empty box, and are never sent anywhere. Every storage access is in try/catch with an in-memory fallback. The per-item remove mark is a mouse affordance only (a `span`, not a button, because a button inside a listbox breaks the pattern); the keyboard way is Delete. "Clear recent searches" is a real button after the listbox.
- Mobile: when the input is focused on a viewport under 1024 px, the same component becomes a full-screen overlay (`fixed inset-0`, body scroll locked, a Cancel button). Same markup, same state, so focus is not lost when it expands.
- If the suggest call fails the box still works: Enter runs the plain search.
- Learn / explain: why `aria-activedescendant` and not moving focus (typing must continue in the input); why the debounce alone is not enough without abort (two slow responses can arrive in the wrong order); why the key includes the settled term.

### 15.6 — mega-menu
- Table `menu_promos` (migration `0017_menu_promos`: pet or null, title, subtitle, image URL and alt text, link, sort order, active; `updated_at` trigger) and `GET /navigation`, one public, cacheable call that builds the whole menu: for each pet, its top-level category's children (with product counts), the brands that sell something buyable for it (one grouped query for all six pets, biggest first, at most 8) and its promo. A pet's own first active promo wins; otherwise the first "any pet" promo; otherwise none. Nothing in it depends on the viewer, so it is mounted before the session middleware with the public cache header. The pet-to-category mapping is a shared constant (`PET_CATEGORY_SLUGS`), not a guess from names.
- Admin: `GET/POST /admin/menu-promos`, `PATCH/DELETE /admin/menu-promos/:id` behind `requireAdmin` and the audit log, and the screen `/admin/navigation`: ordered list, a form with a live preview of the tile, move up and down, hide. A link must be a site path or an `https://` URL (never `//host` or `javascript:`), and the update schema has no defaults, so a PATCH can never refill a field it did not send (a `.default()` inside `partial()` would). Reordering gives two neighbours each other's list position (two small PATCHes), which also survives gaps left by deleted promos. The seed puts one promo per pet plus an "any pet" fallback into an empty table only, using catalogue photos (reptiles: the placeholder illustration) until the lead swaps in promo art.
- Desktop (`MegaMenu`): each pet is a `button` with `aria-expanded` and `aria-controls`, and its panel an ordinary region of links, so this is disclosure navigation, not an ARIA `menu`. Hover opens it after a 150 ms intent delay and closes after one, but nothing depends on hover: Enter, Space and click toggle, Escape closes and puts focus back on the button, Tab walks into the panel and out the other side (leaving closes it), a press outside closes it, and only one panel is open at a time. ### 16.7 — delivery estimate
- `estimateDelivery(now, rules)` in `packages/shared/src/delivery.ts` is pure: the clock is an argument, the STORE's zone (Europe/Amsterdam) decides everything, and the visitor's zone is never used. A business day before 15:00 ships today; after the cutoff, on a weekend or on a holiday it ships the next business day; arrival is the method's min to max business days later. The result carries the countdown in milliseconds (only while an order would still ship today) and a label such as "Cutoff 15:00 CET".
- Time zones done properly: the cutoff instant is found by asking the zone for its UTC offset at that instant (twice, to settle the hour around a clock change), so the countdown is right in the autumn and spring weeks; calendar dates are plain strings and day arithmetic runs at UTC noon. Tests cover before/after the cutoff to the second, Friday after the cutoff, Saturday and Sunday, a holiday as the ship day and during transit, both clock changes, Sunday night UTC being Monday morning in Amsterdam, and a different machine `TZ`.
- `GET /delivery-methods` (public, no cart, not cached) returns each active method's transit days and the server's clock. The product page shows "Order in 4h 20m, arrives Mon 9 Nov to Wed 11 Nov" for standard and the fastest other method below it, ticking once a minute; the countdown is hidden from assistive technology and replaced by a static sentence, so nothing is announced every minute. The Delivery tab states that the schedule is invented.
- Tests: shared 18, API 2, web 15 (pure text, server clock beating a wrong device clock, the tick, the switch at the cutoff, nothing for a sold-out variant).
Learn: inject the clock, name the zone, and test the two weeks a year when a day is 23 or 25 hours long.

### 16.8 — bundles / kits

- Selling a kit moves its components' stock: `expandBundles` turns kit lines into component lines (merging a part that is also bought alone), and checkout reserve, release, paid commit, cancel and refund all go through it. Order items keep the kit variant. The cart prices a kit as a fixed price line, so no sale, member price or code touches it.
- Admin `/admin/bundles`: part picker with search, quantity per part, and a live "parts cost X, the kit saves Y" line that turns red when the price is not under the parts; the server enforces the same rules (two or more parts, no kit in a kit, one currency, price under the parts). Delete archives.
- The kit's page lists what is inside and "Save €3.00 vs individually"; a component's page shows "Make it a kit". Seed adds three dog kits that reuse their first part's photo (follow-up: dedicated kit artwork).
- Tests: shared 7 (saving, valid price, availability); API 10 (admin rules, derived availability, page fields, cart limit by the scarcest part, reserve, release on cancel, commit on paid, merged reservation, refusal when parts run short); web 7.
Learn: derive what can drift (kit stock), store what is a decision (kit price), and give every stock path the same expansion function so no path forgets the parts.

## Phase 17 — Reviews and customer photos

### 17.1 — schema and shared types
- Tables `reviews` (status enum `pending|approved|rejected`, `verified_buyer`, pet context as integer months and grams, unique `(user_id, product_id)`, index `(product_id, status, created_at)`), `review_photos`, `review_votes` (composite PK = one vote per user), `gallery_photos` + `gallery_photo_products`; `products` gains `rating_count` and `rating_sum`. ### 17.3 — photo upload to local disk (committed together with 17.2)

## Phase 19 — Loyalty & retention (steps 19.1–19.6 first, 19.7–19.12 continue in a later run)

### 19.1 — job runner
- `apps/api/src/jobs/runner.ts`: a registry of `{name, every: 'hourly'|'daily', run(ctx)}` and the table `job_runs (name, run_key) unique` (migration `0020_job_runs`). `runJob` claims the period with `INSERT ... ON CONFLICT DO NOTHING`; the first caller owns the period, everyone else is `skipped`. Success sets `finished_at`; a throw deletes the claim so the next tick retries; an unfinished claim older than 15 minutes is a crashed run and is taken over. Registered: `release-stale-reservations` and `activate-sales` (the lazy `syncFlashSales` calls stay as a safety net).
- Three free triggers share it: CLI `pnpm --filter @store/api job run [name]` (cron on any machine), `JOBS_IN_PROCESS=true` (10-minute ticker in `pnpm dev`), and `POST /api/v1/internal/jobs/run` with `X-Jobs-Secret`, called hourly by `.github/workflows/jobs.yml` (which also wakes the sleeping Render service). Later jobs call `registerJob` from their own module.
- Learn / explain: a unique key is a lock that needs no lock service; the key is the period, not the moment, so two triggers 20 minutes apart are the same run; why in-process timers alone cannot be the production plan (a sleeping host misses ticks); why the secret route returns 404 when unconfigured (fail closed).

### 19.2 — points ledger and earning
- Table `points_ledger` (migration `0021_points_ledger`): `delta`, `kind` (earn, redeem, reversal, bonus, donate, adjust), `order_id`, a unique `ref_key`, `reason`. Nothing stores a balance: `balance = SUM(delta)` and the tier comes from lifetime earned points (earn + bonus − earn claw-backs), computed in one aggregate query. Shared `loyalty.ts` holds the tiers (Pup 0, Good Dog 500, Top Dog 2000) and `pointsForCents`, used by the API to award and by the web to say "Earn N points", so the promise and the award are one function.
- Earning is a subscriber of the phase 14 `onOrderPaid` event (`registerLoyaltySubscribers`), inside the transition's transaction. The row is keyed `earn:<orderId>`, so a redelivered webhook, the reconciler and a double event all insert the same key and the second is a no-op (`ON CONFLICT DO NOTHING`). Guests earn nothing (no `userId`). `GET /me/points` returns balance, lifetime, tier, next-tier gap and the last 50 rows; `POST /admin/points/adjust` (admin only) adds an `adjust` row with a reason.
- Web: `EarnPoints` on the product page (per chosen variant) and in the cart summary; a guest sees "Sign in to earn" with a login link that returns to the page.
- Learn / explain: why a ledger and not a balance column (a balance can silently drift from its history; here the history is the balance, and every row says why); why the idempotency key lives in a unique index and not in an `if` (two concurrent events both pass the `if`); why the tier is computed, not stored (a stored tier is a second fact that must be kept in step with the first).

### 19.3 — redeem at checkout and reversal
- `CheckoutRequest.pointsToRedeem`. Inside the existing `placeOrder` transaction: lock the user row (`FOR UPDATE`), re-read the balance under that lock (an order being re-placed gets its own held points back for the check), refuse with a field error if the request is more than the balance, then pass a `points` credit to the phase 18 engine (`promotions.price(..., credits)`). The engine caps it at the merchandise left and keeps it off shipping; whatever it applied is written as the order's one `redeem:<orderId>` row in the same transaction, so the order, its `order_promotions` credit line and the ledger commit or roll back together.
- Reversal is three subscribers on the phase 14 events, in `loyalty/service.ts`: `onOrderCancelled` (a failed or abandoned payment, or a cancelled paid order) and `onOrderRefunded` (full or partial). They add `reversal` rows (never edit): points returned for what was redeemed, earned points taken back (clamped so the balance cannot go below zero by clawing back spent points). Phase 22 only has to emit `onOrderRefunded`.
- Web: the checkout shipping step gets a "Use loyalty points" box whose result is always the server's: the control proposes, the engine decides.
- Learn / explain: why a row lock on the user (a balance read-then-write has a race: both checkouts read 1000 and both spend 800; the lock makes the second read happen after the first write); why the redemption is written in the order's transaction (a crash cannot leave a spent-but-no-order or an order-but-unspent state); why a credit goes through the engine (one place for discount maths, and thresholds look at the merchandise before credits so spending points never loses a gift or free shipping).

### 19.4 — rewards shop and account page
- Table `rewards` (migration `0022_rewards`: name, description, cost in points, kind `coupon_fixed | free_shipping | gift`, value in cents, active; checks keep cost positive and give free shipping no value). `GET /rewards` is public and cacheable (mounted before the session middleware like the catalogue); `POST /me/rewards/:id/redeem` runs one transaction: lock the user row, check the balance, write the `redeem` ledger row, mint the code. `mintPersonalCode` (new `loyalty/codes.ts`) is the one place that creates owner-only, single-use, expiring codes, so referrals (19.6) reuse it. The pricing service now treats a code with an owner as unknown to anyone else, which is what makes "personal" true.
- `/account/rewards`: balance, tier badge and the gap to the next tier, a grid of rewards (a button that says how many points are missing instead of a dead one), the codes already bought with their used or expiry state, and the ledger table (date, what, signed points). Admin: `/admin/loyalty` with rewards CRUD and the points-adjust form; four rewards are seeded into an empty table.
- Learn / explain: why redeem-and-mint is one transaction (a charge without a code, or a code without a charge, are the two bugs customers write in about); why the owner check sits in the pricing path and not in the cart route (the cart is only one of the places a code is used); why a reward mints a code instead of discounting by itself (the engine already handles minimum spend, expiry, usage caps and refunds, and a second path would need all of it again).

### 19.5 — charity
- Tables `charities` (the fictional "Whisker Hollow Rescue", seeded by slug) and `donations` (append-only, `cents` signed by `source`: `points`, `round_up`, `reversal`) plus `orders.donation_cents` (migration `0023_charity_donations`; the order total check now includes the donation). The engine's `roundUpDonation` hook, a no-op until now, rounds the payable total (merchandise after discounts plus shipping) up to the next whole euro: 23.50 gives 0.50, a whole-euro total gives 0, and the amount is its own line, never discounted, included in `totalCents` and so in what Stripe is asked to charge.
- A round-up is recorded when the order is paid (an `onOrderPaid` subscriber, key `roundup:<orderId>` so once per order) and reversed with a negative row when a paid order is cancelled or fully refunded. Points can also be donated (`POST /me/points/donate`, one transaction with the ledger row). `GET /charity/total` (public, cached) is `SUM(cents)` and feeds the footer line and `/charity`. The checkout shipping step has the "round up" checkbox; order summaries, the admin order page and the emails show a "Donation (demo)" line when there is one. Every surface says that no money moves.
- Learn / explain: why a donation is a separate field and not a discount line (a discount can be refunded in proportion, a gift must not be, and the engine must never apply a promotion to it); why the total is a sum of signed rows rather than a counter (a counter cannot say which order it came from, or be corrected without an edit); why counting at the paid event and not at checkout (an abandoned checkout must not inflate a public number).

### 19.6 — referrals
- Tables `referral_codes` (one shareable code per customer, made on first use) and `referrals` (one row per referred account, `referred_user_id` unique; status `pending | qualified | rejected`, the reason, the qualifying order and the two minted codes; migration `0024_referrals`). ## Phase 22 — post-purchase ops

### 22.1 — gateway: partial refunds
- `PaymentGateway.refundPaymentIntent` takes an optional `amountCents`; the Stripe adapter passes it as `amount`, the fake keeps a ledger of refunded cents per intent and refuses to refund more than was charged. `RETURN_WINDOW_DAYS` and `RETURNS_SIMULATED` env flags exist for the later steps.
- Learn: the idempotency key identifies ONE intended refund. Replaying it must return the same answer without moving money again (Stripe remembers keys for 24 h; the fake remembers them for ever). A partial refund per return uses the key `return-<id>`, so a retry after a timeout is safe, while the full-order refund keeps its own key `refund:<orderId>`. Refusing an over-refund is the provider's job, but the fake does it too so a bug in our amount maths fails a test instead of passing silently.
- Tests: api 4 fake-gateway tests (partial then remainder, over-refund and zero rejected, replayed key, already refunded), 1 adapter test (amount sent in cents).

### 22.2 — returns schema and state machine
- `returns` and `return_items` tables, shared enums and labels, and a return state machine with its own table and an exhaustive 25-pair test. The order keeps its status: it becomes `refunded` only when every line is fully returned and refunded (step 22.4).
- Learn: a sub-process with its own life (request, approval, parcel arrives, money back) deserves its own entity and states. Overloading the order status would break "delivered -> refunded" for a partial return and make every order consumer learn about returns. The exhaustive test is the safety net: add a state and it fails until each pair is decided.
- Tests: api 28 state-machine tests (25 pairs, terminal states, rejected frees quantity).

### 22.3 — customer return request
- `POST /orders/:number/returns` and `GET /orders/:number/returns` (owner only). Rules in a pure `assessEligibility` (delivered, window, units left, free lines), the request itself under the order row lock, refunds in integer cents from `price paid - allocated discount`.
- Learn: put the rule in a pure function and the endpoint becomes a thin shell around a lock and an insert. The lock is on the ORDER (not on the return rows): a new return has no row to lock yet, and the order is what every concurrent request has in common. The cumulative-floor split guarantees cents are neither lost nor invented across several partial returns.
- Tests: api 17 (5 eligibility unit tests; 12 endpoint tests: happy path, discount and remainder cent, not delivered, window edge, configured window, over-quantity, duplicate/foreign/free line, 404/401/400, concurrent requests, order stays delivered, eligibility listing) and shared 6 (refund maths, body schema).

### 22.4 — admin return handling, refund and restock
- Admin queue and detail, plus approve, reject (reason), receive (restock) and refund (with an optional shipping refund). A refund is intent -> gateway -> mark; the order turns `refunded` when every paid line is back; each refund emits one `OrderRefunded` event with the amount and lines; five customer emails.
- Learn: money moving is the part you cannot roll back, so write down what you are about to do (the intent row) BEFORE the call, make the call retryable (same idempotency key, same amount), and make the final bookkeeping a no-op the second time. Restock reads the order's own snapshot, never the live catalogue, for the same reason the checkout snapshots a kit: history must not change when the shop edits a product.
- Tests: api 17 in `returns/admin.test.ts` (guard and listing, only-next-state, full flow with exact cents, partial then final return, damaged and subset restock, kit restock after the kit was edited, replayed refund, gateway failure then retry, frozen shipping choice, shipping once, refund after order left delivered, simulated and unconfigured modes, one event per refund, emails and HTML escaping).

## 21.4 String extraction (slice 2)
- Built: `apps/web/src/i18n/` (`useT()` with `t`, `tn`, `tm`; `useFormat()`; typed per-area dictionaries) and every storefront screen (phases 1-22 and 24, including loyalty, wishlist, newsletter, returns, vet, /developers chrome) now reads its text from it. - Learn / explain: the dictionary is typed from the English file, so the compiler is the missing-key detector. Plurals come from the language (`Intl.PluralRules`), not from `n === 1`: German is like English, French counts 0 as singular. ## 21.5 German and French UI strings

## Polish pass: assembly and ship (2026-11-14)
- Built: the API suite made green and fast (tests empty the database with `DELETE` in foreign-key
  order instead of `TRUNCATE`, 40+ min hang → ~7 min), e2e specs updated for the dots-only hero and
  de-conflicted (the demo-helper checkout buys its own product), "You may also like" no longer shows

- Learn / explain: `TRUNCATE` looks like the cheap way to empty a table, but it swaps in new files for
  the table and every index, and Postgres 16 fsyncs each new index file. For a test database that
  holds a few rows, `DELETE` is far cheaper; the order (children first) comes from `pg_constraint`, so
  new tables are handled without a list. A side effect worth knowing: `DELETE` leaves free space in
  the heap, so row order changes, and one test that read "the first row" without an `ORDER BY` or a
  precise filter failed. Tests that depend on physical order are bugs waiting to happen.
